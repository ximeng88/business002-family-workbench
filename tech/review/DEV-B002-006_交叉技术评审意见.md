### 2.2 有问题的项：详细说明

#### R-01（P0）`generationKey` 缺 `childId`

**事实**：`schema.js:63` 对 `tasks` 建了 `&generationKey` —— **全表唯一**。而任务模板支持多孩子（`schema.js:51` 的 `*childIds` 多值索引；`design/05:103` 的"适用孩子集合"）。

**证据**：三处 `generationKey` 样例**都不含 `childId`**：

```
tests/test-utils.js:54          generationKey: "daily:tpl_test:2026-11-18"
tests/database.test.js:117      generationKey: "daily:tpl_test:2026-11-18"
tests/browser-smoke.html:94     generationKey: "daily:smoke:2026-11-18"
```

**后果**：一个模板同时分配给两个孩子时，第二孩子的实例插入会抛 `ConstraintError`（唯一索引），且这个错误发生在**任务生成**环节 —— 表现为"给第二个孩子生成任务时整天失败"，排查成本很高。

**为什么现在必须修**：生成服务还没写。现在改的是**契约**（样例 + 注释 + 一条测试），成本几行；等 P-P2 写完再发现，要改生成逻辑 + 迁移已有数据。

**建议**：
1. 在 `schema.js` 注释与 `05` §2.4 写明格式：`${type}:${childId}:${templateId}:${dateKey}`；
2. 补一条测试：**同一模板、同一日期、两个孩子**各生成一条，且都成功（这条测试现在会挂，正好证明问题存在）；
3. 反向补一条：同孩子同模板同日重复生成 → 抛 `ConstraintError`（幂等仍然成立）。

#### R-02（P0）`reviews.eventKey` 的"留空"必须实现为"不写该属性"

**事实**：`schema.js:86-88` 写的是"退回记录的 `eventKey` 留空，不使用该唯一约束"。但 `eventKey` 上有 `&`（唯一索引，`schema.js:89`）。

**证据**：`tests/database.test.js:132` 断言 `where("generationKey").equals("").count() === 0` —— 这条断言本身证明：**空字符串是合法键值、会被索引进唯一索引**。所以"留空"若被实现为 `eventKey: ""`，第一条退回记录写入后，**第二条退回（任何孩子的任何任务）都会撞唯一索引**。

**后果**：退回功能上线当天，第二次退回全站失败，事务回滚，家长看到"这次没成功，再点一次"，但再点也一样。这属于"上线即坏"的级别。

**建议**：
1. `schema.js` 注释改成明确表述：**退回记录不得写 `eventKey`（`delete` 该属性 / 不赋值），不接受 `""`、`null`、`0`**；
2. 在交付/交接里与 `tasks.generationKey`（临时任务同理，`schema.js:58-59` 已写对）归为同一条纪律："稀疏唯一索引 = 不写属性，不是写空值"；
3. 测试补一条：连续两条退回记录写入成功。

> 这条是本轮**最有价值的一条**：它不是现在的 bug（退回服务还没写），而是**下一步几乎必定踩的坑**，而且踩中后症状与"幂等生效"高度相似，容易被误诊。

#### R-03（P1）三表不一致态没有出口

任务书 §4.3 点名的场景（`reviews` 无记录，但 `pointLedger` / `petProgress` 已有同 `eventKey`），代码实际行为：

| 分支 | 实际行为 | 安全性 |
|---|---|---|
| 预检只查 `reviews`（`approval.service.js:103`） | 未命中 → 继续 | — |
| 任务仍 `submitted`，`ledger` 已有该 `eventKey` | 走到 `pointLedger.add` → `ConstraintError` → 事务整体回滚 → `catch` 只回查 `reviews`（`:235`）→ 查不到 → 抛 `wrapDbError` → **`DB_UNIQUE_CONFLICT`** | **安全但无出口**：不会重复发放（对），但家长看到的是"唯一索引冲突（同一事件被重复写入）"（`errors.js:128`），既不准也不给动作 |
| 任务已 `approved`，三表**都**没有记录 | 返回 `already-approved`，不写任何表（`:120-127`） | **静默**：孩子永远拿不到这笔奖励，且无任何提示 |

**判断**：这两条都不会**多给**，属于"失败关闭"（fail-closed），是可接受的工程取向。问题在**可诊断性与可恢复性**：不一致态是"数据已经坏了"，却复用了"你点了两次"的文案。

**建议**（不要求本轮修）：
1. 新增错误码 `DB_INCONSISTENT_STATE`，文案面向家长："这条记录的数据对不上，建议先导出备份再从备份恢复"，并给出 P-P5 入口；
2. 预检时顺带查 `pointLedger` / `petProgress` 的 `eventKey`（一次 `count()`，成本可忽略），命中即判 `inconsistent`；
3. 补一条测试：构造"有流水无审核记录"的库，断言返回 `inconsistent` 而非 `duplicate` 或裸 `ConstraintError`。

#### R-04（P1）`streaks` 用确定性主键查询

```js
// approval.service.js:194-210
const streakId = `${task.childId}:${approvalDate}`
const existingStreak = await db.streaks.get(streakId)
if (existingStreak) { ... update ... } else { ... add ... }
```

`streaks` 同时有 `&[childId+date]`（`schema.js:116`）。只要库内存在一条 `childId` 与 `date` 匹配、但 `id` 不是 `${childId}:${date}` 的记录（历史数据、迁移、恢复后人工修复、将来改 id 规则），`get()` 会返回 `undefined` → 走 `add` → 撞唯一复合索引 → **整个审核事务回滚**。

**影响面**：单条坏数据会让"这个孩子这一天"的所有审核永久失败，而错误信息只会说"事务失败"。

**建议**：改用复合索引查询，不依赖主键格式 ——

```js
const existing = await db.streaks.where("[childId+date]").equals([task.childId, approvalDate]).first()
```

#### R-05（P1）读取失败与打开失败共用错误码

`errors.js:110`：`if (phase === "read") return DB_ERROR_CODES.OPEN_FAILED`。

但设计 `02` §8.5 把这两件事分得很清：I2（单表读取失败 → **页内错误卡**，其他区块正常）vs I3（库打不开 → **全屏异常页**）。同一个错误码，界面层只能二选一，无论选哪个都错：

- 映射到全屏页 → 违反 I2 与 IR-40（"不得因单表失败跳全屏终止页"）；
- 映射到错误卡 → 库真的打不开时显示成"任务暂时打不开"，家长不会去走恢复流程。

**建议**：新增 `DB_READ_FAILED`，并在 `05` §3 补一张"错误码 → 界面格（I1–I5 / W1–W3）"的映射表。这张表页层一定会用到，晚写就等于让 Trae 临场发挥。

#### R-06（P1）`ensureMetadata` 会给半成品库盖章

```js
// database.js:59-78，被 openDatabase 在每次打开成功后调用（:97）
const existingVersion = await table.get("schemaVersion")
if (!existingVersion) { await table.put({ key: "schemaVersion", value: SCHEMA_VERSION, ... }) }
```

时序上：恢复流程建了新库、写了结构、**写到一半失败**（明文要求"不得留下半成品库"）→ 下次打开 → `openDatabase` 成功 → `ensureMetadata` 补写 `schemaVersion` → 这个库在结构上"看起来已初始化"。

`tech` §6.3–6.5 要求 `_meta.restoreState` 作为完成标记、启动时**先判状态再决定是否补写**。当前 `restoreState` 只在注释里（`schema.js:134`），没有代码。

**建议**：恢复功能落地时，`ensureMetadata` 必须让位给"启动检查"：顺序为 `open → 读 _meta → 无 restoreState 且库内无业务数据 → 才视为新装并写元数据`。现在就要把这条写进 `05`，否则实现时极可能保持现状。

#### R-07（P1）`_meta.schemaVersion` 不会随版本升级更新

只写一次的写法，在 v2 迁移后仍保留 `1`。后果：备份文件里的 `schemaVersion`、`readSchemaVersion()` 的结果、诊断信息全部偏差一格，而恢复校验第 ③ 项（版本兼容）正是看这个值。

**建议**：在 `SCHEMA_VERSIONS` 的每个 `upgrade` 末尾显式写 `_meta.schemaVersion`；或 `ensureMetadata` 比对 `db.verno` 与实际记录不一致时以 `verno` 为准修正。补一条测试：升级到 v2 后 `readSchemaVersion() === 2`。

#### R-08（P1）流水排序字段与业务日期不同源

`points.service.js:69-76` 用 `[childId+createdAt]` 倒序分页，`createdAt` 是 **UTC ISO**（`date.js:48-54`）。而 `approvalDate` 是**本地自然日**。

东八区 00:00–07:59 发生的审核，两者会落在不同日期：

```
本地 2026-11-20 00:30 审核
  createdAt   = "2026-11-19T16:30:00.000Z"   ← 截前 10 位 = 11-19
  approvalDate = "2026-11-20"                ← 连续记录记在 11-20
```

数据层没写错（谁也没说 `createdAt` 是业务日期）。风险在 UI：P-P4 若要按日分组，最省事的写法 `createdAt.slice(0,10)` 会显示 11-19，而 P-C4 显示 11-20 那天连续达标 —— 同一个行为在两个页面显示成两天，家长一定会来问。

**建议**：在 `05` §2.3 / §3 的 P-P4 段写死两条：① 分组用 `approvalDate`（或本地时区格式化 `createdAt`）；② **禁止**对 ISO 字符串截前 10 位当日期。若 P-P4 需要按日聚合，考虑给 `pointLedger` 加 `approvalDate` 索引。

#### R-09（P2）`submissions.status` 无枚举，审核不回写

`schema.js:66-80` 只有索引与注释，没有 `status` 取值定义；`approval.service.js` 全程不碰 `submissions`。

提交服务落地时会出现一个必答题：**任务 `approved` 之后，提交记录的 `status` 应该变成什么？** 不定，就会出现"任务页显示已通过、P-P3 详情里提交记录仍是待审"的两套真相。

**建议**：提交服务轮次定义枚举（建议 `submitted` / `returned` / `accepted` / `superseded`），并明确"审核通过是否在同一事务内同步提交记录"。若同步，则五表事务变六表，**必须写进 `PROJECT_STATE` 与设计文档**，否则会与冻结规则"五表原子事务"字面冲突。

#### R-10 / R-11 / R-12 / R-14 / R-15（P2，记录）

- **R-10**：`adjustPoints` 的 `eventKey = manual:${entryId}`（`points.service.js:137`）每次新生成，等于**没有幂等**。PRD §10 只强制 approval 与 redemption 幂等，但手动扣分同样不可逆。页面层必须禁用按钮；若要更稳，可让调用方传 `requestKey`。
- **R-11**：`contentType` 只在注释里限定 `"text"`（`schema.js:72`）。Dexie 不做字段校验，所以这条约束只能在提交服务里用代码保证。
- **R-12**：`getDb()` 单例只接受默认库名（`database.js:41-49`），`closeDb()` 后重建仍用 `DB_NAME`。`tech` 方案 B 需要"指针指向哪个库就用哪个库"，因此恢复轮次**必须新增** `setActiveDb(name)` 或 `openNamedDb(name)`。`createFamilyDatabase(name)` 已经具备能力，差一个入口。
- **R-14**：`isDateKey()`（`date.js:36-45`）写得很严谨（拒绝 2026-02-30），但全仓零调用。任务创建 / 导入时若不调用，`dueDate` 就可以是 `"2026-2-3"`、`"今天"`、时间戳，而逾期判定 `dueDate < today` 会静默给出错误结果。
- **R-15**：宠物只有 `petProgress` 经验流水，没有等级/当前经验状态表。这**符合 PRD §7.3**（经验记录至少含流水 ID / 孩子 / 变化值 / 事件键 / 任务 / 时间），且等级可由 `cumulative exp` 对照阈值（PRD §7.2）派生 —— 比再存一份状态更不容易不一致。问题只在**文档没写清**：`design/05:113-117` 描述的是"等级 / 当前经验 / 升级所需经验"，页层照此实现很可能再造一张 `pets` 表或往 `children` 里塞字段，制造第二真相。建议下一轮设计修订时，把 `05` §2.3 的宠物段改为"等级 = 由 `petProgress` 累计值对照阈值派生，**不建状态表**"。

### 3.1 Q-05 `expPerPoint`：**有条件通过**（不是写死，但也不是可配置）

逐条回答任务书 §4.1 的五个问题：

1. 结构层完全中立：`petProgress` 与 `pointLedger` 分表、分索引、分常量，`exp` 不参与任何余额计算；
2. 系数是**入参**，不是硬编码字面量出现在业务判断里（`:142` 用的是变量）；
3. 测试里的固定预期**会让改系数时亮红灯**，这是"可见的耦合"，不是"静默冻结"——静默冻结是指改了系数测试照样绿、界面照样显示 1:1。

1. 把 `8.2-1` 与冒烟页的断言改成"显式传 `expPerPoint` 并断言 `exp === round(points × 传入值)`"，另加一条**单独**验证"默认值是 1"的测试，注释写清"仅验证默认值，非产品规则"。这样 Q-05 一旦改判，只需要改那条默认值测试；
2. 给系数留一个**配置入口**（`settings.expPerPoint`，缺省回落到常量）。现在是页层必须记得传参，漏传就悄悄回到 1:1 —— 这类"默认值兜底"在生产里几乎必定被漏。

### 3.4 测试环境与 E4 假设：**需补证据**

**（1）17 项浏览器冒烟覆盖了什么**

我把 `browser-smoke.html` 的 17 个 `check()` 全部读了一遍，清单是：

```
打开库 → schemaVersion=1 → 表数量=12 → 写孩子/读回 → 写任务/读回
```

**全是成功路径 + 重复拦截**。**没有一条失败注入**：没有模拟事务中途失败、没有模拟配额不足、没有模拟唯一索引冲突、没有验证回滚。

- "17/17 PASS" 可以支持"**主路径在真实浏览器引擎上跑通**"；

## 7. 页面开发的推荐顺序

### 7.1 先孩子端还是家长端

**先孩子端 P-C1 → P-C2，但必须同时做家长端 P-P3（审核）。**

理由：产品价值只在"审核通过"那一刻发生。只做孩子端，等于做一个只能提交、永远不结算的界面——数据层最值钱的那部分（五表事务）得不到真实验证；只做家长端，则没有可审的东西。**P-C2 + P-P3 这一对，是本项目唯一能"一次跑通全链路"的最小切片。**

### 7.2 依赖最少 / 最多

| 页面 | 数据依赖 | 新服务需求 | 难度 |
|---|---|---|---|
| **P-C1 身份选择** | `children` 读 | 无 | **最低**。是天然的第一页，也顺带把"空家庭态（I5）"验掉 |
| **P-P3 待确认中心** | `tasks where status=submitted` | **已就绪**（`approveTask` 可直接用）；缺退回服务 | 低。**数据层验证价值最高** |
| **P-C2 今日任务** | `tasks` 双查询（今日 + 逾期全量） | 缺：任务创建/生成、提交服务（文字） | 中。折叠规则易做错（见 §8） |
| P-P1 孩子列表 | `children` + 每孩子进度 + `settings.lastBackupAt` | 缺：PIN 会话 | 中（PIN 门控） |
| P-P2 任务管理 | `taskTemplates` CRUD + 生成 | 缺：生成幂等（R-01 落点） | 中高 |
| P-C3 宠物与积分 | `petProgress` 汇总 + `pointLedger` | 缺：等级派生纯函数；**需 Q-05 口径** | 中 |
| P-C4 连续学习 | `streaks` | 缺：连续天数纯函数；**需 Q-02 口径** | 中（算法小，口径重） |
| P-P4 积分与奖励 | `pointLedger` + `rewards` + `redemptions` | 缺：兑换事务（幂等扣分） | 高 |
| **P-P5 设置与备份** | `settings` | 缺：PIN/恢复码、导出、**导入/恢复（方案 B 全套）**、删除 | **最高** |

### 7.3 建议批次

**批次 0（前置工程，不算页面，约 1 天）**
`启动接入 + 四态兜底页 + 错误码映射` → `临时任务创建（P-P2 的最小子集）` → `文字提交服务` → `退回服务`
> 不做这一步，"批 1"会变成"做两个不能互相验收的页面"。这一步同时把 P0 的 1–4 项修掉。

**批次 1（主闭环切片，最有价值）**
`PIN 最小闭环（设置 / 校验 / 恢复码展示）` → `P-C1` → `P-C2（读 + 四状态 + 逾期折叠 + 提交）` → `P-P3（通过 / 退回）`
> 一次跑通：布置 → 提交 → 审核 → 积分 → 经验 → 连续，六个环节全部在真实 UI 上验证。这一批做完，项目才算"能演示"。PIN 必须在这里做，因为**所有家长页都被它门控**，越晚做返工越多。

**批次 2（激励与配置）**
`P-P2（模板 + 生成幂等，验证 R-01）` → `P-C3（宠物/积分）` → `P-C4（连续）`
> 依赖 Q-03 / Q-05 / Q-02 三项裁决。若 Owner 未裁决，这三页只做骨架、数值区留占位，不要临时拍一个数先上。

**批次 3（钱与命）**
`P-P4（兑换，幂等扣分）` → `P-P5（备份 / 恢复 / 删除全部数据）`
> 最重、最容易出事故，也最不该赶。P-P5 直接对应 `tech` 方案 B（临时库 + 指针切换 + 完成标记），需要先把 R-06 / R-07 / R-12 修掉。

### 7.4 "必须先补服务才能做某页"的依赖清单

```
P-C1  ← 无（只读 children）
P-C2  ← 任务创建/生成 + 文字提交服务
P-P3  ← PIN 会话 + 退回服务（审核服务已就绪）
P-P1  ← PIN 会话 + 每孩子进度汇总（可复用 getBalance / streaks）
P-P2  ← 模板 CRUD + 生成幂等（generationKey 定型）
P-C3  ← 等级派生函数 + Q-05 口径
P-C4  ← 连续天数纯函数 + Q-02 口径
P-P4  ← 兑换事务（幂等扣分）+ rewards CRUD
P-P5  ← PIN/恢复码 + 导出 + 导入/恢复（方案 B）+ 删除（G-05）
```

## 8. 全局风险与建议

### 8.1 六条最容易在实现层被丢掉的约束

| # | 约束 | 丢法 | 后果 | 检测方法 |
|---|---|---|---|---|
| 1 | **逾期折叠只在渲染层**（IR-31） | 图省事在查询里 `limit(3)` | 折叠区里的任务提交后，家长端取不到 → **永久卡在"待确认"**，且家长看不到任何异常 | code review 搜 `limit(` 出现在 `tasks` 查询链上；补一条测试：4 条逾期任务，第 4 条提交后出现在 `status=submitted` 查询结果里 |
| 2 | **审核按钮禁用 ≥300ms + 事务后一次性刷新**（IR-06 / IR-05） | 做"乐观更新"（先变绿再等结果） | 事务失败时孩子已经看到了加分动画 | review 搜 `optimistic` / 手动检查"事务 await 之前有没有改 DOM" |
| 3 | **家长端不得有"直接改余额"**（IR-12） | 做一个"编辑星星数"输入框 | 余额与流水脱钩，此后所有对账失效 | review 搜 `balance` 赋值 |
| 4 | **孩子端禁红 + 全站禁"同步/云端/网络错误"文案**（`04` / `02` §0） | 顺手用了通用组件库的红色 error 样式 | 违背产品红线，且误导家长以为有后端 | 文案 grep：`同步`、`云端`、`网络`、`离线模式` |
| 5 | **K18 不加清理** | 以"性能优化"名义加 TTL / 归档 | 历史数据静默消失，且不可恢复 | review 搜 `before(`、`delete`、`clear` |
| 6 | **IR-40 计数失败显示"—"不显示 0** | `count()` 的 catch 里返回 0 | 家长看到"0 颗星星"以为数据被清空，可能去做错误的恢复覆盖 | review 每一个 `count()` / `length` 的 catch 分支 |

### 8.2 待裁决项会在哪一页实际撞上

| 编号 | 撞上的页面 | 撞上的具体位置 |
|---|---|---|
| **Q-03** 每周必选星期 | P-P2 | 表单必填校验、多选交互 |
| **Q-05** 经验系数 | P-C3 | 成长条数值文案（"再攒 X 点就升级"用的是经验还是星星） |
| **Q-02** 连续天数断点 | P-C4 | 大数字算法（今天没做时显示 N 还是 N-1） |
| **Q-11①** 历史回看入口 | P-P1 / P-P4 | 有没有"看以前"的入口，直接决定页面数 9 还是 10 |
| **G-05** 删除全部数据 | P-P5 | 危险分组的入口与否决（设计已完整，否决只需删一个入口） |
| **G-01 剩余**（文字长度上限 / 是否在卡片上展示提交内容） | P-C2 / P-P3 | 卡片结构与截断规则 |

### 8.3 给 Owner 的裁决顺序建议

按"下一批页面什么时候需要它"排，不要按编号排：

```
1. G-01 正式关闭（含：文字提交的长度上限、卡片上是否展示正文）
      → 页面开发第 0 步就要用，不定就没法做提交框
2. Q-03（每周必选星期、可多选）
      → 批次 2 的 P-P2 表单，但它同时决定 generationKey 的组成，越早越省事
3. Q-05（经验系数）
      → 批次 2 的 P-C3；若定 1:1，数据层已可用，无需改动
4. Q-02（连续天数断点）
      → 批次 2 的 P-C4；这是唯一"算错会让孩子每天早上莫名归零"的一项，值得单独想清楚
5. Q-11①（历史回看是否进第一版）
      → 批次 3 之前定即可，但它改页面数，会影响验收清单
6. G-05 确认（不否决即视为通过）
      → 批次 3
```

**两条我认为最值得优先的**：G-01 剩余部分（否则提交框做不出来）、Q-02（口径错会产生"每天归零"的体验事故，而这种事故很难被家长描述清楚，排查成本极高）。

### 8.4 一个流程建议

本轮暴露了一个结构性风险：**设计文档 v0.4 与数据层实现已经开始漂移**（G-01 状态、宠物模型、错误码分层）。漂移不可怕，可怕的是没有回收点。

本轮需结清的三条：G-01 状态回写、宠物模型（R-15）、`_meta` 第 12 张表（`tech` §2.1 表清单）。
