## 1. 结论摘要

### 1.1 推荐架构（一句话）

**写入全新的临时库 → 库内写"完成标记" → 逐项校验 → 通过后才切换应用指向 → 重载 → 确认可用后再清理旧库。**

即设计侧列出的**方案 B**，并叠加"旧库延迟删除"（方案 C 的轻量形态）。理由与限制见 §5。

### 1.2 七条判据全部可在切换前完成

七条判据（写入无异常 / 库可重开 / 分表计数 / 关联完整 / 余额汇总 / 宠物经验 / 附件可读）**全部在临时库上执行**。这是方案 B 的核心优势：校验失败时正式库从未被触碰，用户手上的旧数据完好。E3。

### 1.3 三条关键限制（必须先看）

| # | 限制 | 影响 | 等级 |
|---|---|---|---|
| L1 | IndexedDB 事务在"等待非 IDB 异步操作"时会自动提交，长事务上限由浏览器实现决定，规范未定义 | 不能承诺"一个大事务写完所有数据"，尤其含 Blob 时 | E2（自动提交）/ E4（上限） |
| L2 | IndexedDB 没有库重命名 API，切换库必须靠"外部指针"（localStorage / cookie / 扫描库列表） | 引入一个必须容错的指针层 | E2 / E4 |
| L3 | 方案 B 在切换前需要同时容纳"旧库 + 新库" | 空间峰值翻倍；含照片时风险显著 | E3 |

### 1.4 若评审否决方案 B

降级顺序：**B → C（保留旧库更久）→ A（就地清空写回）**。方案 A 可用，但必须叠加"导入前自动备份"（PRD §11.5 已要求）作为唯一回退依据，并接受"写入期间本机无可用数据"的空窗。详见 §5.6。

| 原备份文件 | 全程只读，不删、不移、不改名 | design IR-34 原则 5 |

### 2.2 术语

- **正式库**：应用正常业务读写的库（当前生效）。
- **临时库**：恢复过程中新建、用于承接备份数据的库，未切换前业务代码不读它。
- **完成标记**：写在库自身 `_meta` 表里的显式状态，表示"本次写入已完整结束"。
- **指针**：IndexedDB 之外保存的"当前正式库名"记录。
- **切换**：把指针改写为新库名并重载应用的动作。

## 3. 备份文件格式（恢复的输入契约）

### 3.1 顶层结构（建议）

```json
{
  "format": "b002-family-backup",
  "formatVersion": 1,
  "schemaVersion": 1,
  "appVersion": "0.0.0",
  "exportedAt": "2026-11-19T23:00:00+08:00",
  "deviceLabel": "Windows · Chrome 131",
  "manifest": {
    "children": 2,
    "taskTemplates": 9,
    "tasks": 128,
    "submissions": 128,
    "reviews": 96,
    "pointLedger": 340,
    "rewards": 6,
    "redemptions": 4,
    "petProgress": 340,
    "streaks": 41,
    "settings": 1,
    "attachments": 0
  },
  "derived": {
    "pointTotals": { "c_1": 120, "c_2": 85 },
    "pet": { "c_1": { "level": 3, "exp": 20 }, "c_2": { "level": 2, "exp": 5 } },
    "ledgerCounts": { "c_1": 210, "c_2": 130 },
    "petLedgerCounts": { "c_1": 210, "c_2": 130 }
  },
  "attachmentsMeta": [
    { "id": "a_1", "mime": "image/jpeg", "byteLength": 812344, "sha256": "…" }
  ],
  "data": {
    "children": [], "taskTemplates": [], "tasks": [], "submissions": [],
    "reviews": [], "pointLedger": [], "rewards": [], "redemptions": [],
    "petProgress": [], "streaks": [], "settings": [],
    "attachments": [{ "id": "a_1", "dataBase64": "…" }]
  }
}
```

要点：

1. **`formatVersion` 与 `schemaVersion` 必须分离**。前者是文件容器版本，后者是数据库结构版本。迁移时可能只升其中一个。E3。
2. **`manifest` 记录每张表条数**，是判据 3 的比对基准，也是第 ③ 步"恢复摘要"的数据来源（design 要求摘要含每表条数）。E1（设计规定）。
3. **`derived` 记录导出时点的派生值**，是判据 5 / 6 的比对基准。**不得**把它实现成库里的可写字段——它只在备份文件里作为"期望值"。E2（PRD 冻结"余额派生"）。
4. 缺 `formatVersion` 的文件直接判 F1（design IR-35 ③）。E1（设计规定）。

### 3.2 分卷与流式（对未来的约束）

第一版按**单文件 JSON**设计。但格式里预留两条不破坏兼容的空间：

- `data` 下每个分区是数组，允许未来拆成外部引用（`{"__ref": "part-3.json"}`）。
- `attachments` 数组允许改为"二进制容器引用"。

**为什么预留**：分支 A（照片）下 base64 内嵌的体积与内存峰值可能不可接受（§11.2.3）。现在不实现，但格式不能写死成"只能是内联 base64"。E3。

### 3.3 版本兼容策略

| 情形 | 处理 |
|---|---|
| `formatVersion` 本应用不认识 | F1「这个备份是别的版本做的」 |
| `formatVersion` 认识、`schemaVersion` 较低 | 允许恢复，写入后执行迁移函数（迁移需注册表，见 §12） |
| `schemaVersion` 高于本应用 | F1，不尝试降级 |
| 缺少 `schemaVersion` | F1（视同"必需字段缺失"） |

**禁止**"尽力而为"地导入未知版本：字段缺失会产生"看起来正常"的残缺家庭（design IR-35 禁止项）。E1（设计规定）。

## 4. 九步业务流程的技术落地

### 4.1 总表

| 步 | 设计动作 | 技术动作 | 失败出口 | 证据 |
|---|---|---|---|---|
| 1 | 选文件 | `<input type="file">` 或 `showOpenFilePicker()`；**不打开任何数据库** | 取消 → 回上页 | E2 |
| 2 | 内存校验 | 读文件 → 解析 JSON → IR-35 七项 → 汇总 manifest；同时 `estimate()` 做空间预检 | F1 | E2 / E4（大文件） |
| 3 | 摘要 + 确认 | 渲染摘要弹层；确认按钮点击后立即 `disabled` | 取消 → 回上页，库不动 | E1（设计） |
| 4 | 重建目标库 | 生成临时库名 → `new Dexie(name)` → `open()` → 写 `_meta.restoreState='writing'` | **F3** | E2 / E4 |
| 5 | 写入 | 结构化数据单事务；Blob 分批（分支 A）→ 最后写 `restoreState='complete'` | **F2** | E2 / E4 |
| 6 | 校验 | 七条判据逐条执行（§7） | **F2** | E2 |
| 7 | 更新元数据 | 在**新库** `settings` 写 `lastRestoreAt`；**不改** `lastBackupAt` | 失败按 F2 | E1（设计） |
| 8 | 重载 | 先写指针，再 `location.reload()` | 指针写失败 → 不重载，按 F2 | E3 |
| 9 | 收尾 | 启动时读指针 → 打开新库 → 校验 `restoreState` → 提示一次 → 清理旧库 | 校验失败 → 异常页 | E3 |

### 4.2 第 2 步：为什么必须"在库之外"

设计要求"校验阶段不得创建、清空、迁移任何业务库"。技术上必须做到：

- 文件读取用 `File.arrayBuffer()` / `File.text()`，全程不实例化 Dexie。E2。
- JSON 解析后先做**结构校验**（字段存在性、类型），再做**引用校验**（内存里建 `Set` 比对），最后做**计数校验**（与 `manifest` 比对）。E3。
- 校验期间**内存占用 ≈ 文件字节数 × 2～3**（原始字符串 + 解析后的对象图）。这是 E3 推导，实测值待验证（E4）。因此大文件必须分块（§4.4）。

### 4.3 正常导入（库可用）与异常恢复（库不可用）的差异

| 维度 | 正常导入（P-P5） | 异常恢复（异常页） |
|---|---|---|
| 起点 | 正式库可打开 | 正式库打不开或无库 |
| 写入目标 | 临时库（同方案 B） | 临时库 |
| 旧库处置 | 切换成功后删除 | 旧库本就不可用，切换成功后尝试删除（失败不影响） |
| 自动备份 | **必须先自动备份当前数据**（PRD §11.5） | 无数据可备份，跳过 |
| 失败后状态 | 正式库完好，用户回到 P-P5 | 仍为异常页，可再试 |
| 指针写入 | 必需 | 必需 |

**关键结论**：两条路径**只有"是否需要自动备份"和"失败后回到哪"不同**，写入与校验内核完全一致。这正好满足设计侧"两者共用同一套校验与落盘规则，但路径不同"（IR-34）。E1（设计）/ E3（实现推论）。

### 4.4 大备份的内存与分块

| 手段 | 做法 | 风险 |
|---|---|---|
| 文件大小预检 | 读文件元信息 `file.size`，超过阈值（建议 50 MB）先提示"文件较大，检查会慢" | 阈值本身是经验值，E4 |
| 分块读 | `file.slice(0, n)` 逐块读入并做 JSON 流式解析 | 需要流式 JSON 解析器；第一版若不做，退化为"整读 + 大小上限" |
| 分块哈希 | 逐块 `crypto.subtle.digest` 无法直接流式（需整块），可对每个 Blob 单独算哈希 | 单 Blob 哈希可行，E2 |
| 计数校验不依赖全量 | 分表条数从 `manifest` 读，不必把 `data` 全读进内存后再数 | 降低峰值 |

**诚实说明**：第一版**建议**"整文件读入 + 50 MB 硬上限 + 超限提示换文件"，而不是流式解析。理由：整份备份在分支 B（无附件）下通常只有几百 KB～几 MB；流式 JSON 解析器引入复杂度和新依赖。E3。若 G-01 裁决含照片，则必须重新评估（§11.2.3）。

## 5. 三种写入方案比较（核心）

### 5.1 方案 A：清空现有库 → 写回原库

```
deleteDatabase(正式库) 或 逐表 clear()  →  重新 open  →  写全部数据  →  校验
```

**优点**：无指针层、无多库管理、代码最少。
**致命缺陷**：写入开始后旧数据已不存在。若第 5 步中途失败或页面被关闭，用户恢复到的状态是"没有库"或"半成品库"，只能靠完成标记拦在 F2——而**此时没有任何可用的回退数据**（异常场景下连旧库都没有）。E3。
**缓解**：依赖"导入前自动备份"生成的内部备份文件。但该文件本身也在 IndexedDB 里（若存库里就一起被清了），必须存到 **OPFS 或 Cache Storage** 才有效——这又增加了实现面。E3 / E4。
**适用**：只有在"方案 B 的指针机制被证明不可行"时才降级采用。

### 5.2 方案 B：临时库 → 校验 → 切换（推荐）

```
创建临时库 tmp_<ts>  →  写 restoreState='writing'
  →  写数据（结构化单事务；Blob 分批）
  →  写 restoreState='complete'
  →  七条校验（全部在临时库上）
  →  写指针 activeDb = tmp_<ts>
  →  reload
  →  启动读指针 → 打开新库 → 校验 complete → 提示一次
  →  异步删除旧库（失败则留到下次启动重试）
```

**优点**：

1. 校验失败时正式库零损伤（这是 design IR-34 原则 4 的直接满足）。
2. **允许分批写入**，从而绕开长事务上限（L1）。这是解决"单事务写大量数据不可行"的正当路径。
3. 崩溃后的中间态天然不可见：业务代码只打开指针指向的库，临时库名不匹配任何业务路径。
4. 旧库可延迟删除，形成事实上的回滚窗口。

**缺点**：

1. 需要指针层（L2），且指针存储必须容错。
2. 空间峰值接近翻倍（L3）。
3. 多标签页需要协调（§6.6）。

### 5.3 方案 C：可回滚（旧库长期隔离）

```
方案 B  +  旧库改名为 bak_<ts> 并保留 N 天  +  设置页提供"回到恢复前"入口
```

**优点**：用户可在恢复后发现"恢复错了"并回退。
**缺点**：空间长期双份；需要新增 UI 与"回退"这一业务语义；回退后又要处理"在此期间新产生的数据"（合并还是丢弃），复杂度陡增。

**结论**：第一版**不做用户可见的回滚入口**，但采纳 C 的"延迟删除"部分（旧库先改名隔离，确认新库可用后删除）。这样保留了技术上的退路，不引入业务语义。E3。

### 5.4 十维比较表

| 维度 | A 就地清空写回 | B 临时库切换 | C 可回滚 |
|---|---|---|---|
| 数据安全（失败时旧数据） | **差**（已清空） | **好**（正式库未动） | **最好**（旧库保留） |
| 原子性 | 依赖单事务，做不到就半成品 | 天然原子（切换是最后一步） | 同 B |
| 页面崩溃 | 见半成品库，需标记拦截 | 临时库成孤儿，业务不可见 | 同 B |
| 额外空间 | 无 | **约 +1 份（旧库+新库）** | +1 份且长期占用 |
| 大型备份可行性 | 受长事务限制 | **好**（可分批） | 好 |
| IndexedDB 长事务限制 | **直接受影响** | 可规避 | 可规避 |
| 浏览器兼容 | 无额外要求 | 需动态库名 + 指针存储 | 同 B + 删除/改名 |
| 恢复速度 | 快（无二次打开） | 略慢（多一次 open + 校验） | 同 B |
| 可回滚性 | **不可** | 有窗口（旧库未删前） | 显式入口 |
| 第一版实现复杂度 | 低 | **中**（指针 + 多库 + 状态机） | 高 |

**评分结论**：B 在 6 个维度最优、2 个维度中、1 个维度差（空间）；A 只在"复杂度/空间"占优，但这两项恰好可以通过工程手段控制，而"数据安全"无法补偿。**推荐 B + 延迟删除**。E3（综合判断，非实测）。

### 5.5 推荐方案的关键实现约束

| # | 约束 | 理由 |
|---|---|---|
| R1 | 业务代码**只能**通过 `resolveDbName()` 取库名，不得出现硬编码库名 | 否则切换后旧代码仍指向旧库 |
| R2 | 指针**双写**：localStorage + cookie；读取时 localStorage 优先 | 单一存储被清时仍可自愈 |
| R3 | 指针全缺失时，回退为 `indexedDB.databases()` 扫描，选 `_meta.restoreState==='complete'` 且 `createdAt` 最大者 | 兜底 |
| R4 | 扫描能力不可用时（老浏览器），回退到固定主库名 `b002_main` | 保证有路可走 |
| R5 | 写入完成标记**必须写在库内** `_meta`，不能只写指针 | 指针与数据可能不同步 |
| R6 | 切换前必须 `db.close()` 所有连接 | 否则后续删除被 blocked |
| R7 | 旧库删除失败不算恢复失败 | 只影响空间，不影响正确性 |

R2/R3/R4 的每一步都是可失败点，因此指针层必须写成"**读不到就用默认值**"的纯降级逻辑，绝不抛错阻塞启动。E3 / E4（`indexedDB.databases()` 兼容性见 §14）。

### 5.6 若必须用方案 A 时的补充要求

1. 清空前**强制**导出内部备份到 OPFS（不能存 IndexedDB 自身）。E4（OPFS 兼容性需验证）。
2. 逐表 `clear()` 必须在单事务内；事务外不得有写操作。E2。
3. 写入前先写 `restoreState='writing'`，写完全部数据后写 `'complete'`；启动时只要看到 `'writing'` 就拦在 F2。E3。
4. 空间预检的安全系数提高（因为失败后无旧库可依）。

### 5.7 单事务写 Blob 的可行性（问 2）

| 情形 | 结论 | 等级 |
|---|---|---|
| 无 Blob（分支 B） | 结构化数据量小（数千条、几 MB），单事务写入**原理上可行**；实际耗时取决于设备 | E3 / 耗时 E4 |
| 含 Blob（分支 A） | **不建议承诺单事务**。Blob 体积可达数百 MB，长事务会触发浏览器限制或内存峰值 | E3 / 限制 E4 |
| 替代方案 | 结构化数据单事务；Blob 按"每批 ≤ 20 MB 或 ≤ 50 个"分批；每批一个事务；全部完成后写 `complete`。因目标库是临时库，分批不产生"对用户可见的半成品" | E3 |
| 前提 | 分批方案**只能**在方案 B 下使用。方案 A 下分批等于制造可见半成品 | E3 |

这是本文档对设计侧"单事务写 Blob 可行性"问题的正式回答：**单事务不是必须的，把"原子性"转移到"临时库 + 完成标记 + 最后切换"上，可以同时满足两条硬要求**（满足七判据 + 不留可见半成品）。

## 6. 半成品库识别与状态机（问 3）

### 6.1 七个问题逐条回答

| # | 问题 | 回答 |
|---|---|---|
| 1 | 完成标记存哪里 | **目标库自身的 `_meta` 表**，键 `restoreState`。不放在 localStorage（指针与数据可能不同步），不放在 settings 业务表（会被业务逻辑误读） |
| 2 | 恢复开始时如何记录状态 | 创建临时库后的**第一个事务**写 `_meta = { restoreState:'writing', sourceBackupHash, startedAt, targetDbName }` |
| 3 | 数据写完但校验失败 | 临时库写 `restoreState='failed'`（同库内再开一个事务）；**指针不切换**；正式库不动；按 F2 提示 |
| 4 | 写入中途崩溃 | 临时库里仍是 `'writing'`。启动时指针未指向它，业务不可见；清理器识别为孤儿 → 删除或标记 |
| 5 | 启动时如何判断库可进入业务 | `resolveDbName()` → `open()` → 读 `_meta.restoreState`；**必须 `==='complete'` 才进入业务**；缺失/`'writing'`/`'failed'`/读不到 → 异常页 |
| 6 | 如何防止半成品被业务使用 | 三重：①库名隔离（临时库名不在业务路径）②指针最后才切换 ③`_meta` 守卫在启动入口强制检查 |
| 7 | 状态记录本身损坏 | 视为**不可用**（不是"当作正常"）；转异常页并提供"从备份恢复"；**不得**回退到"没有标记就按正常处理" |

### 6.2 库命名规则

```
正式库：  b002_main                 （首次初始化）
临时库：  b002_tmp_<yyyyMMddHHmmss>_<rand4>
隔离旧库：b002_bak_<yyyyMMddHHmmss>_<rand4>
```

- 前缀 `b002_` 用于扫描归类。
- 时间戳用于"最新的 complete 库"兜底排序。
- `rand4` 防止同一毫秒并发。E2（字符串唯一性，数学）。

### 6.3 `_meta` 表结构（最小）

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | string | 主键。仅两条：`restoreState`、`createdAt` |
| `value` | any | 状态值 / 时间戳 |

或扁平化为单条记录：

```js
{ id: 'meta', restoreState: 'writing'|'complete'|'failed', createdAt, sourceBackupHash, startedAt, completedAt, appVersion, schemaVersion }
```

**建议单条记录**：一次读全，减少一次事务。E3。

**为什么单独一张表而不是塞进 `settings`**：`settings` 是业务表，会被导出、会被迁移、会被"删除全部家庭数据"清空；`_meta` 不应参与业务导出（它不是家庭数据），也不该被业务查询意外读到。E3。

### 6.4 状态转换

```
                    ┌──────────────┐
   打开成功且 complete ──▶│   normal     │
                    └──────────────┘
                           ▲
                           │ 切换指针 + reload
                    ┌──────────────┐
   创建临时库 ──────▶│   writing    │──写入/校验失败──▶ failed
                    └──────────────┘        │
                           │ 全部写入+校验通过  │
                           ▼                  ▼
                    ┌──────────────┐   ┌──────────────┐
                    │   complete   │   │ 废弃/删除     │
                    └──────────────┘   └──────────────┘
```

补充规则：

- `normal` 不是库内状态，而是"指针指向的库 `_meta` 为 complete"这一外部判定结果。E3。
- `failed` 的临时库**不切换指针**，但保留到本次会话结束再删（便于导出诊断）。E3。
- 不存在 `'empty'` 状态：删除全部家庭数据后，库仍是 `complete`（只是数据为空），由一个独立业务标志 `initialized=false` 表达（§10.5）。**两者不能混用**。E3。

### 6.5 启动检查算法

```
function boot():
  name = localStorage['b002.activeDb'] ?? cookie['b002_active'] ?? scan()
  if name == null:                       # 从未初始化
      name = 'b002_main'
  try:
      db = openDb(name)
  except:
      # 库打不开：先看是否有可用的其它候选库
      alt = scanComplete()
      if alt != null and alt != name:
          name = alt; db = openDb(name)
      else:
          return Screen.I3_ABNORMAL
  meta = read(db, '_meta')
  if meta == null or meta.restoreState != 'complete':
      # 有可能是"首次安装"：只有确认库内无 _meta 且无任何业务数据时才按新装处理
      if meta == null and isEmpty(db):
          return bootstrapNew()          # 走 I5 空态，与新装一致
      return Screen.F2_INCOMPLETE        # 明确的"恢复未完成"
  return Screen.NORMAL
```

关键判断：**"`_meta` 缺失"与"有业务数据但 `_meta` 缺失"必须区分**。前者可能是首次安装（老版本库没有 `_meta`），后者是半成品。E3。

> 迁移注意：若未来从"无 `_meta` 的 v1"升级到"有 `_meta` 的 v2"，升级事务里必须补写 `complete`，否则老用户会被判成半成品。这条是**实现时必须处理**的坑，记录在 §13。

### 6.6 崩溃场景矩阵

| 崩溃时点 | 库内状态 | 指针 | 启动结果 | 用户看到 |
|---|---|---|---|---|
| 创建临时库后、写数据前 | `writing` | 未变 | 业务不可见；清理器删孤儿 | 正常旧数据（正常导入）／异常页（异常恢复） |
| 写入中 | `writing` | 未变 | 同上 | 同上 |
| 写完但未校验 | `writing` | 未变 | 同上 | 同上 |
| 校验通过、未写指针 | `complete` | 未变 | 临时库成孤儿，**可被兜底扫描选中** | 旧数据（下次选文件恢复时可覆盖） |
| 写了指针、未 reload | `complete` | 新 | reload 后进新库 | 正常（数据已恢复） |
| reload 后、删旧库前 | `complete` | 新 | 正常；旧库残留 | 正常 + 占空间 |

**结论**：只有"指针已切换但新库有问题"是危险组合，而它在写指针之前已通过七条校验，所以风险极低。E3。

### 6.7 多标签页

| 场景 | 处理 |
|---|---|
| 恢复时另一标签在用旧库 | 恢复开始前用 `BroadcastChannel('b002')` 广播 `restore:begin`；其他标签显示"正在恢复，请勿操作"并 `db.close()` |
| 切换后旧标签仍在跑旧库 | 广播 `db:switched`，旧标签强制 `location.reload()` |
| `BroadcastChannel` 不可用 | 降级用 localStorage `storage` 事件 |
| 两者都不可用 | 第一版接受风险：在恢复入口提示"请关闭其他标签页" |

`BroadcastChannel` 在现代浏览器普遍支持（Safari 15.4+）。E2 / 具体版本 E4。

## 7. 七条判据的技术落地（问 4）

### 7.1 逐条对照

| # | 判据 | 技术做法 | 失败判定 | 成本 |
|---|---|---|---|---|
| 1 | 写入无异常 | `await db.transaction(...)` resolve；捕获 `AbortError` / `QuotaExceededError`；检查 `tx.done` | 抛错或 `tx.done` reject | 极低 |
| 2 | 库可重新打开 | `db.close()` → `new Dexie(name)` → `open()` → 读 `db.verno` 与 `_meta.schemaVersion` 一致 | 打开抛错 / 版本不符 | 一次 open |
| 3 | **分表记录数一致** | `for t of tables: await db.table(t).count()` 与 `manifest[t]` 逐表相等 | 任一表不等 | O(n) 遍历，见 7.3 |
| 4 | 关键关联完整 | 先取各表主键 `Set`，再校验：`tasks.childId ∈ children`、`tasks.templateId ∈ templates`、`reviews.taskId ∈ tasks`、`pointLedger.childId ∈ children`、`redemptions.rewardId ∈ rewards`、`submissions.taskId ∈ tasks`、`petProgress.childId ∈ children`、`streaks.childId ∈ children`；同时检查备份内主键无重复 | 任一孤儿 / 悬空 / 重复 | O(n)，内存 O(主键数) |
| 5 | 积分汇总正确 | 按 `childId` 累加 `pointLedger.delta` → 与 `derived.pointTotals` 相等；流水条数与 `derived.ledgerCounts` 相等 | 不等 / 出现非法值（NaN、非整数） | O(n) |
| 6 | 宠物经验完整 | 读 `petProgress` 当前等级/经验 → 与 `derived.pet` 相等；经验流水条数与 `derived.petLedgerCounts` 相等；**不得**用积分合计代替 | 不等 | O(n) |
| 7 | 附件可读（依赖 G-01） | 分支 A：`count` 与 `manifest.attachments` 相等；`sum(blob.size)` 与 `attachmentsMeta` 总字节相等；随机抽 1–3 张 `await blob.arrayBuffer()` 且长度匹配，图片再 `createImageBitmap(blob)` 解码成功。<br>分支 B：**跳过**并在日志与诊断信息里记 `attachmentCheck: 'skipped(no-attachment-scope)'` | 不等 / 解码失败 | 抽样解码较贵（几十 ms/张） |

### 7.2 抽样（不是第八条判据）

- 判据 3、5 在计数通过后，**必须**随机抽 3–5 条完整读出，检查关键字段非空、类型正确、值合理（时间戳可解析、积分 delta 为整数）。
- 抽样只作为"数量对但内容空"的防线，不单独计为判据。E1（设计要求）。

### 7.3 逐表计数的成本

- IndexedDB 的 `count()` 对**无索引过滤**的整表计数通常走主键遍历，复杂度 O(n)。E3。
- 分支 B 下 11 张表、总量约 1k–1万条，总耗时预计在**几十毫秒到数百毫秒**。E4（未实测）。
- 分支 A 下若把 Blob 与元数据放同一表，`count()` 只数条目不读 Blob，成本不变。这是"附件独立表"的另一个理由。E3。
- **优化**：`count()` 可并行发起（同一事务内或多个只读事务）。注意 Dexie 的事务内并发能力有限，建议逐表串行，避免事务过多。E3 / 并发收益 E4。

## 8. 存储空间预检与持久化（问 6）

### 8.1 `navigator.storage.estimate()` 的边界

| 事实 | 说明 | 等级 |
|---|---|---|
| 返回 `{ usage, quota }` | `usage` ≈ 已用，`quota` ≈ 配额上限 | E2 |
| `quota` **不是**可用磁盘空间 | 它是浏览器按启发式给出的上限，可能远大于或小于真实剩余空间 | E2 |
| 不同浏览器差异大 | Chrome 较宽松，Firefox / Safari 更保守 | E2 / 具体比例 E4 |
| 可能返回不精确值或 0 | 隐私模式、新配额策略下可能拿不到 | E4 |

**因此：`quota - usage` 只能作为"看起来够 / 可能不够"的依据，绝不能表述为"空间足够"。** 这与 design IR-35 前置表完全一致。E1（设计要求）+ E2（API 语义）。

### 8.2 `persist()` / `persisted()`

| 项 | 说明 | 等级 |
|---|---|---|
| `persist()` | 请求"持久化"，成功后浏览器在空间紧张时**更不容易**清理本应用数据 | E2 |
| `persisted()` | 查询当前是否已持久化 | E2 |
| 授权策略 | Chrome 按启发式自动授予（安装、书签、通知、参与度）；Firefox 弹窗；Safari 行为不同 | E2 / E4 |
| 拒绝处理 | 拒绝**不影响可用性**，只影响被清理概率；必须仍允许正常使用（PRD §11.1） | E1（PRD） |
| 调用时机冲突 | PRD §11.1 要求"应用启动时"，design IR-18 要求"首次进入家长模式（非阻断）" | **G-04 已登记，未裁决** |
| Safari ITP | 长期未访问的站点，脚本可写存储可能被清理；`persist()` 未必豁免 | E2（ITP 存在）/ E4（当前版本行为） |

### 8.3 预检算法（建议）

```
needed ≈ backupFileSize × 0.78            // base64 解码后的结构化近似
       + (分支 A ? attachmentsBytes × 1.0 : 0)
       + (方案 B ? currentDbUsage × 1.0 : 0)   // 新旧库并存
safety  = 1.5                             // 经验系数
warn if (quota - usage) < needed × safety
```

- `0.78` 来自 base64 的 4/3 膨胀反算（数学，E3）。
- `currentDbUsage` 可用 `estimate().usage` 近似，但它包含整个源站的存储，不单是本库；不精确。E3 / E4。
- 系数 `1.5` 是经验值，**没有任何实测依据**，属**未验证假设**，评审可改。
- 预检结果**只用于提示，不阻止继续**，文案必须含"可能"（design IR-35 前置表）。E1（设计要求）。

### 8.4 空间不足或估算不可靠时

| 情形 | 行为 |
|---|---|
| 空间明显不足 | 提示"这台设备的空间可能不够，恢复有可能中途停下"，**不阻止**，由家长决定 |
| 估算不可用（API 缺失 / 返回 0） | 不显示数字，改为通用提示"如果设备空间紧张，恢复可能会中途停下" |
| 写入时真的 `QuotaExceededError` | 事务 abort → F2，文案"手机空间不够了"；临时库删除；正式库不动 |
| 估算够但实际不够 | 同样走 F2；**不得**因此把判据 1 判成通过 |

### 8.5 大 Blob 的额外空间风险

- 方案 B + 分支 A：峰值 ≈ 旧库（含旧照片）+ 新库（含新照片）+ 备份文件本身在磁盘上。
- 若备份 300 MB，旧库 300 MB，则峰值可能超过 600 MB + 文件。E3。
- **建议**：分支 A 下空间预检系数上调至 2.5，并在摘要中明确显示"恢复期间会同时占用旧数据与新数据两份空间"。E3。

## 9. 失败与终止态（问 1 的失败面）

### 9.1 三类失败的技术判定

| 类型 | 技术触发点 | 判定依据 | 数据现状 |
|---|---|---|---|
| **F1 文件问题** | 第 1–2 步 | 读文件异常 / JSON 解析失败 / 版本不符 / 结构缺失 / 引用断裂 / 规模异常 | 正式库未触碰 |
| **F2 恢复中断** | 第 5–6 步 | 事务 abort / `QuotaExceededError` / 任一判据不过 | 正式库完好（方案 B）；临时库标记 `failed` 并删除 |
| **F3 环境不可用** | 第 4 步 | `open()` 抛错且重试一次仍失败（仅判断"能否建库"，不是业务错误） | 无新库；旧库不动；文件完好 |

**F3 的判定必须只看"建库"**，不能把"文件校验失败"算进 F3。E1（设计要求）。

### 9.2 终止的是本次流程

实现上必须避免两个错误：

- **不写"永久失败"标记**（例如把 `restoreState='terminal'` 持久化到某个长期存储）。终止态只是**本次会话的界面**，刷新后重新从 I 组判定开始。E1（设计要求）。
- **不在终止页放"立即重试"**。同环境重试必然再失败。E1（设计要求）。

### 9.3 原备份文件的保护

技术上本项目**没有删除用户文件的权限**（浏览器沙箱）。因此"原文件保留"是天然满足的，只需保证：

- 不调用 `showSaveFilePicker` 的删除、不改写用户选择的 `File` 对象。
- 不诱导用户"恢复失败请删掉这个文件再试"。E2（沙箱机制）。

这是本文档唯一一条可以明确说"物理上不可能违反"的设计要求。E2。

### 9.4 旧库与临时库的清理

| 对象 | 清理时机 | 失败处理 |
|---|---|---|
| 临时库（`writing`/`failed`） | 本次会话结束前，或下次启动扫描时 | 删除失败不报错，留到下次 |
| 旧库（`bak_`） | 切换成功且新库通过启动检查后 | 删除失败保留，下次重试；连续 3 次失败提示家长"可在浏览器设置里清理站点数据" |
| 孤儿库（无指针引用、非 `bak_`、非当前） | 扫描时 | 同上 |

**删除库的正确姿势**：`db.close()` 所有连接 → `indexedDB.deleteDatabase(name)` → 监听 `blocked` 与 `success`。若 `blocked` 长时间不解除，放弃本次删除。E2。

## 10. 删除全部家庭数据（G-05）的可靠性（问 7、8）

### 10.1 清空方式

**推荐：单事务逐表 `clear()` + 同事务写"未初始化"标志。**

```
db.transaction('rw', ALL_TABLES, async () => {
  for (const t of ALL_TABLES) await db.table(t).clear();
  await db._meta.put({ id:'meta', restoreState:'complete', initialized:false, clearedAt: now });
})
```

| 备选 | 评价 |
|---|---|
| `indexedDB.deleteDatabase()` | 更彻底、更快，但**不是事务**，且无法在同一步写状态；失败/阻塞判定模糊；删掉后连 `_meta` 都没了，无法区分"从未装过"与"刚清空" | 
| 逐表独立事务 | **禁止**：违反"全成或全败"，正是"部分删除"的来源 | 
| 单事务逐表 `clear()` | **推荐**：IDB 事务原子性保证全成或全败 | 

**结论**：用单事务 `clear()`，不用删库。E2（事务原子性）。

### 10.2 成功判定三条

| # | 判定 | 技术做法 |
|---|---|---|
| 1 | 事务提交无异常 | `transaction` promise resolve |
| 2 | 清空后重开库校验为**空** | `db.close()` → 重开 → 对每张业务表 `count() === 0` |
| 3 | 不自动生成 | 读 `_meta.initialized === false`，启动逻辑据此跳过一切"每日任务生成" |

三条全过才显示"已经删除了"。E1（设计）/ E3（实现）。

### 10.3 失败三档的识别

| 档 | 技术特征 | 判定 | 文案 |
|---|---|---|---|
| 全回滚 | 事务 abort，重开后各表 count 与删除前一致 | 可精确判定 | 「没删掉，数据还是原来的」 |
| 部分删除 | **正常实现下不应出现**（单事务原子） | 若出现，说明实现走了多事务或跨库操作——属缺陷 | 「有一部分删掉了，有一部分还在」+ 标注不完整 |
| 读不出 | 重开失败 / 查询抛错 | 转异常页 | 不得说"已删除" |

**必须写进实现规范的硬约束**：清空只允许"一次 `db.transaction` 包住所有表"，代码评审时逐条检查。E3。

### 10.4 防遗留（"只删孩子却遗留任务/积分/宠物/附件"）

- 清空的表清单**写成一个常量数组**，与导出/恢复共用同一份清单，避免三处各写一套。E3。
- 清单必须包含：11 张业务表 + `_meta`（改写而非清空）+ 分支 A 的 `attachments`。
- 若未来新增表，**必须**同时加入该清单；建议在 Schema 定义处用注释强约束。E3。
- Blob 清理：`attachments.clear()` 在事务内；注意"删记录 ≠ 立即释放磁盘"（IDB 异步压缩），文案不得承诺"空间立刻回来"。E3。

### 10.5 "不自动生成今天的任务"（问 8）

需要一个**显式的初始化标志**，而不是靠"表为空"推断：

| 方案 | 评价 |
|---|---|
| 靠 `children.length === 0` 推断 | **不可靠**：用户删完孩子但保留模板时，表不空 |
| 靠 `settings.exists` | 尚可，但 `settings` 被清后与"首次安装"无法区分 |
| **`_meta.initialized` 布尔** | **推荐**：删除时置 `false`，首次设置 PIN 完成时置 `true` |

启动逻辑：`initialized !== true` → 只允许走"首次设置"流程，不生成任务、不弹恢复提示。E3。

### 10.6 与恢复的隔离

- 两者**不共用**任何入口、文案、状态机（design IR-41 硬要求）。
- 技术上两者唯一的共享是"表清单常量"——这是代码复用，不是流程合并。E3。
- 异常页/终止态页**不加载**删除入口的代码路径（路由不可达）。E3。

## 11. G-01 分支条件设计（不裁决，只给两套可执行分析）

### 11.0 共同不变量（两分支都必须成立）

1. 孩子提交 → `tasks.status = 'submitted'`，**不产生任何积分或经验**。
2. 只有家长在 P-P3 点"通过"才发积分与经验（五表原子事务）。
3. 若"家长确认"被定义成一种提交方式，它也只能把任务送入 `submitted`，**不能直接发放奖励**。
4. `submissions` 表在任何分支下都存在（记录提交历史），只是字段多少不同。

### 11.1 分支 A：第一版支持文字 + 照片提交

#### A-1 表与字段

```js
// submissions：一次提交一条记录（退回后重新提交即新增一条）
{
  id: 'sub_xxx',
  taskId: 't_xxx',
  childId: 'c_xxx',
  attempt: 1,                  // 第几次提交
  mode: 'text' | 'photo' | 'confirm',
  text: '...',                 // mode=text 时必填，≤500 字
  attachmentIds: ['a_1'],      // mode=photo 时必填，≥1
  submittedAt: 1732000000000,
  revokedAt: null              // 第一版不开放撤回，预留为 null 常量
}
// 索引：taskId, [childId+submittedAt], [taskId+attempt]（唯一）

// attachments：独立表
{
  id: 'a_1',
  submissionId: 'sub_xxx',
  taskId: 't_xxx',
  childId: 'c_xxx',
  mime: 'image/jpeg',
  byteLength: 812344,
  sha256: '...',               // 导出/校验用
  blob: Blob,                  // 结构克隆，直接存 Blob
  createdAt: 1732000000000
}
// 索引：submissionId, taskId, childId
```

`tasks` 上**不新增** `photoUrl` / `text` 字段。理由：一个任务可被退回并多次提交，内容属于"提交"而非"任务"。E3。

#### A-2 Blob 内联 vs 独立表

| 维度 | 内联（`submissions.blob`） | 独立表（`attachments`） |
|---|---|---|
| 读取成本 | 列表查询会把 Blob 一并读出（Dexie 读取整条记录） | 可分表读元数据，不碰 Blob |
| 事务大小 | 单条记录变大，单事务写入更易触限 | 可按批写入，粒度可控 |
| 备份序列化 | 结构简单 | 需要按 `attachmentIds` 关联导出 |
| 删除 | 清 `submissions` 时随行删除 | 需显式清 `attachments` |
| 恢复 | 单表 | 两表 + 关联校验（增加判据 4 的检查项） |
| 索引效率 | 大记录会让索引变大 | 索引只覆盖元数据 |

**推荐：独立表。** 决定性理由是 P-P3 审核列表：家长一屏要看多条提交，若 Blob 内联，一次 `toArray()` 会把所有照片读进内存。E3。

#### A-3 备份内嵌 base64 的体积膨胀

| 项 | 估算 | 等级 |
|---|---|---|
| base64 膨胀率 | `4/3 ≈ 1.333`，即 +33.3% | E3（数学恒等） |
| JSON 字符串内存 | 每字符 2 字节（UTF-16 常见实现），base64 字符串内存 ≈ 原始字节 × 1.333 × 2 | E3（实现相关，E4） |
| 10 张 2 MB 照片 | 原始 20 MB → base64 26.7 MB → 字符串内存 ~53 MB → 解析峰值再翻倍 | E3 |
| 100 张 2 MB 照片 | 原始 200 MB → base64 267 MB → 单文件 JSON 不可行 | E3 |
| 导出耗时 | 主要受 base64 编码 + `JSON.stringify` + 落盘影响，200 MB 级预计数十秒并可能 OOM | E4 |

**结论与建议**：

1. 若 Owner 裁决含照片，**必须**同时决定"单次提交照片数量与体积上限"（建议：每次 1 张、≤5 MB、必要时前端压缩到 ≤2 MB）。没有上限就没有可用的备份格式。E3。
2. 单文件 JSON + base64 的**可用区间**约在"照片总量 ≤ 30–50 MB"。超过则应改为：
   - **方案 A-α**：ZIP 容器（`manifest.json` + 原始二进制文件），无膨胀、内存峰值低，但需要引入压缩库（如 `fflate`，体积小）。
   - **方案 A-β**：导出时提供"不含照片"选项（PRD 未禁止，但需 Owner 批准，属新决策 **G-08**）。
3. 第一版若坚持 JSON，应在导出前**预检照片总量**，超过阈值直接提示并给替代路径，而不是让用户等到导出失败。E3。

**由此产生一个新的待裁决项：G-08（备份容器是否必须为单文件 JSON）。** 记录在 §12.2，不自行裁决。

#### A-4 恢复校验中"附件可读"的判定

按 design IR-37 第 7 条，需同时满足三项：

| 项 | 做法 | 备注 |
|---|---|---|
| 数量一致 | `attachments.count()` vs `manifest.attachments` vs `submissions.attachmentIds` 去重后的数量 | 三者必须相等 |
| 字节一致 | `sum(blob.size)` vs `sum(attachmentsMeta.byteLength)` | 需要遍历，O(n) |
| 抽样可解码 | 随机 1–3 张：`arrayBuffer()` 长度 == `byteLength`；图片再 `createImageBitmap(blob)` 成功 | `createImageBitmap` 在部分浏览器对某些格式失败，需区分"格式不支持"与"数据损坏" |

**实现注意**：`createImageBitmap` 不可用时（老 Safari）降级为"读头 12 字节校验魔数（JPEG `FFD8FF`、PNG `89504E47`）"。E2 / E4。

#### A-5 空间预检如何因附件而调整

- `needed` 加上 `attachmentsBytes`（解码后，≈ base64 长度 × 0.75）。
- 方案 B 下再叠加 `currentDbUsage`（旧库含旧照片）。
- 安全系数建议 2.5（而非 1.5）。
- 摘要弹层必须显示"恢复期间会同时占用新旧两份空间"。E3。

#### A-6 孩子端提交界面的数据契约

| 字段 | 来源 | 规则 |
|---|---|---|
| `taskId` | 当前卡片 | 必填 |
| `childId` | 会话中的孩子 | 必填，服务端（本地）二次校验任务归属 |
| `mode` | 用户选择（文字/拍照） | 必填；若"家长确认"是第三种方式，此处也多一个枚举值，但提交后仍为 `submitted` |
| `text` | 输入 | `mode=text` 时必填，长度上限（建议 500） |
| `attachmentIds` | 拍照/选图后写入 `attachments` 的返回值 | `mode=photo` 时 ≥1；建议上限 1–3 |
| `submittedAt` | 提交时刻 | 由应用写入，不接受前端传入 |

**提交事务**：`tasks` 状态更新 + `submissions` 插入 + `attachments` 插入（若先存了 Blob 则此处仅关联）必须在**同一事务**内，否则会出现"任务已提交但没有照片"或"照片存在但任务未提交"。E3。

**版本语义**：`attempt` 递增；退回后重新提交产生新记录，旧的保留（K18 精神：不删历史提交）。E3。

#### A-7 对恢复方案的影响

| 影响 | 说明 |
|---|---|
| 单事务写入 | 不可承诺；改为"结构化单事务 + Blob 分批"（§5.7） |
| 恢复耗时 | 显著上升；需分段进度（设计已要求"正在恢复数据 3/7"） |
| 空间 | 峰值翻倍，可能触发 F2 |
| 校验 | 判据 7 成为必须项 |
| 备份体积 | 需引入 G-08 决策 |
| 删除 | 必须清 `attachments`，否则"删了记录留下二进制" |

### 11.2 分支 B：第一版不支持照片/文字，只保留"点击完成" + 家长确认

#### B-1 `submissions` 最简结构

```js
{
  id: 'sub_xxx',
  taskId: 't_xxx',
  childId: 'c_xxx',
  attempt: 1,
  submittedAt: 1732000000000
}
// 索引：taskId, [childId+submittedAt], [taskId+attempt]（唯一）
```

**为什么仍然保留这张表**：①PRD §9.3 明确列出 `submissions`；②`tasks` 只有一个 `status`，无法表达"提交过几次"；③未来加附件时，附件需要挂在"提交"上而不是"任务"上。E3。

#### B-2 未来加附件的迁移路径（加字段，不重建表）

IndexedDB 的记录是无模式的键值对象，**新增字段不需要重建表**，只需要：

1. `db.version(n+1).stores({ ... })` —— **仅当需要新索引时**才写 `stores`；不新增索引可只 bump 版本。
2. 旧记录缺字段 → 读取时按默认值处理（`mode ?? 'confirm'`、`attachmentIds ?? []`）。
3. 新增 `attachments` 表：在 `stores` 里追加一条即可，Dexie 会自动创建。

**这保证了分支 B → 分支 A 是"增量迁移"，不是"重建"**——正好回答设计侧"结构不写死"的要求。E2（IDB/Dexie 版本机制）。

**反向不成立**：若是分支 A 已经上线再砍回 B，Blob 表可以保留不用，但备份格式已经含附件分区，需要版本降级处理。E3。

#### B-3 恢复校验中附件项如何跳过而不影响其他判据

| 做法 | 说明 |
|---|---|
| 判据 7 显式标记 `notApplicable` | 校验函数的返回结构里，第 7 项返回 `{ status: 'skipped', reason: 'scope:no-attachment' }`，**不是** `pass` |
| 汇总规则 | 1–6 全 pass + 7 skipped → 判定成功；1–6 任一 fail → 失败。**不得**因为 7 是 skipped 就放宽 1–6 |
| 界面与日志 | 诊断信息里写明"本次备份不含附件，附件校验未执行"，避免 QA 误以为漏做 |
| 未来兼容 | 若读到的备份里**有** `attachments` 分区（来自旧的高版本），按分支 A 的规则校验，不因当前代码不支持就跳过 |

这条"备份里有附件就必须校验"很关键：**跳过与否取决于备份内容，而不是取决于当前代码版本**。E3。

#### B-4 与 PRD §5.3 的差异记录

- PRD 原文：三种提交方式 + 照片原图存本地库。
- 分支 B：只实现"点击完成（= 家长确认）"。
- 处理：**PRD 不改**；本方案与实现中标注「**第一版裁剪范围待 Owner 批准（G-01 分支 B）**」，并在交付报告与 `PROJECT_STATE.md` 的待裁决表里保持 G-01 为"未裁决"。
- 禁止：把"无附件"写成冻结规则，或从 PRD 中删掉该要求。E1（设计/任务书规定）。

### 11.3 两分支对数据模型的差异汇总

| 项 | 分支 A | 分支 B |
|---|---|---|
| `submissions` 字段数 | 8 | 5 |
| 新增表 | `attachments` | 无 |
| 新增索引 | `attachments.submissionId` 等 | 无 |
| 备份分区 | 12 + `attachmentsMeta` | 11 |
| 单事务写入 | 不可承诺（需分批） | 可行 |
| 恢复耗时 | 高 | 低 |
| 空间风险 | 高（峰值翻倍） | 中 |
| 判据 7 | 必须 | 跳过（记录原因） |
| 删除范围 | 含 `attachments` | 11 表 |
| 额外决策 | 照片上限、备份容器（G-08） | 无 |

### 11.4 明确不裁决

本文档**不判断哪个分支更好**，也不建议"先做 B 后加 A"作为产品结论（那是 Owner 的范围决定）。技术事实只有一条：**分支 B → 分支 A 是增量迁移，改造成本远低于 A → B**；但分支 A 一旦上线，备份格式与空间策略都会显著变复杂。E3。

| 5 | 库名指针方案（localStorage + cookie + 扫描） | **待验证** | 需在目标浏览器验证 localStorage 可写、`indexedDB.databases()` 可用 |
| 6 | 单事务写入实际耗时与上限 | **待验证** | 分支 B 必测；分支 A 需测分批阈值 |
| 7 | `count()` 在真实数据量下的耗时 | **待验证** | 1 万条级实测 |
| 8 | `estimate()` 在目标浏览器的返回质量 | **待验证** | Chrome / Safari / iOS |
| 9 | `persist()` 授权行为 | **待验证** | 三种浏览器差异 |
| 10 | Safari / iOS 的 Blob 存取可靠性 | **待验证**（仅分支 A） | 写入、读回、导出三轮 |
| 11 | 多标签页协调（BroadcastChannel） | **待验证** | 两标签并发恢复 |

| 13 | 字段命名与索引定稿 | **待实现** | 依赖 #1 |

## 14. 验证边界清单

### 14.1 按结论归类

| # | 结论 | 等级 | 依据 / 风险 |
|---|---|---|---|
| 1 | 事务在等待非 IDB 异步操作时会自动提交 | E2 | MDN「Transaction」：事务在无待处理请求时提交 |
| 2 | IDB 事务不具备跨页面/跨会话持久性 | E2 | MDN |
| 3 | `deleteDatabase` 在有其他连接时会被 `blocked` | E2 | MDN「IDBDatabase/deleteDatabase」 |
| 4 | IndexedDB 没有 rename 库的 API | E2 | MDN API 列表 |
| 5 | 记录存储无模式，新增字段不需重建表 | E2 | MDN「Object store」/ Dexie 版本机制 |
| 6 | Dexie 支持 `new Dexie(动态库名)` 与多实例 | E2 | Dexie 文档 Dexie 构造函数 |
| 7 | `estimate()` 返回 `{usage, quota}`，`quota` 是估算上限 | E2 | MDN「StorageManager.estimate」 |
| 8 | `persist()` 授权是启发式，可能被拒绝 | E2 | MDN「StorageManager.persist」 |
| 9 | base64 膨胀 4/3 | E3 | 数学恒等 |
| 10 | 整份 JSON 解析的内存峰值约为文件 2–3 倍 | E3 | 字符串 + 对象图，具体倍率 E4 |
| 11 | 方案 B 可规避长事务限制 | E3 | 推理：分批写入 + 完成标记 + 最后切换 |
| 12 | 方案 B 的空间峰值约为两倍 | E3 | 旧库 + 新库并存 |
| 13 | 单事务 `clear()` 全成或全败 | E3 | 由 IDB 事务原子性推出 |
| 14 | `clear()` 后磁盘空间不会立即释放 | E3 | IDB 异步压缩，未实测 |
| 15 | 浏览器沙箱使应用无法删除用户文件 | E2 | 文件系统访问模型 |
| 16 | **长事务的具体上限（秒/MB）** | **E4** | 需在 Chrome / Safari / iOS 分别测"单事务写入 N MB"的失败点 |
| 17 | **临时库切换的实际耗时** | **E4** | 需实测 open + reload 的总时长 |
| 18 | **iOS Safari 上 Blob 恢复是否可靠** | **E4** | 需实测写入/读回/导出三轮 |
| 19 | **`indexedDB.databases()` 兼容性与行为** | **E4** | Firefox/Safari 版本差异 |
| 20 | **`count()` 在 1 万条量级的耗时** | **E4** | 需实测 |
| 21 | **多标签页广播的可靠性** | **E4** | 需实测 |
| 22 | **安全系数 1.5 / 2.5 是否合理** | **未验证假设** | 纯经验值，无数据支撑，评审可改 |
