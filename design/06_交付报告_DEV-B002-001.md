## 四、设计决策记录（我做的判断，需 Owner 知晓）

以下 20 项是在冻结摘要之外、由设计侧做出的判断。**它们不是产品规则的修改，而是规则落到界面时必须做的选择**。若 Owner 或 ChatGPT 有不同意见，按第五节流程修订。

| 编号 | 决策 | 理由 | 影响范围 |
|---|---|---|---|
| D-01 | 身份选择是"门"不是 Tab；冷启动一律回身份选择，不记忆上次身份 | 多孩共用一台设备，记忆会导致进错账号，且孩子会看到别人的任务 | 01 §2.1、IR-13 |
| D-02 | 家长端 = 4 个 Tab + 设置放右上角齿轮 | 设置是低频动作，占 Tab 位会挤掉高频入口；同时避免 5 个 Tab 在小屏上文字挤压 | 01 §3、02 §3.6 |
| D-03 | **"离线"降级为常态，取消离线业务态**。全站禁止"离线模式/同步中/网络错误"文案，只保留 3 个真实网络场景（首次安装、版本更新、安装引导） | 本项目无后端，断网时功能完全一致。给一个不存在降级的应用加"离线态"，是照搬有后端产品的设计惯性，会造成用户误以为功能受限 | 02 §0、§1 |
| D-04 | 页面级不使用骨架屏/加载态 | 本地 Dexie 读取 < 100ms，骨架屏只会产生"闪一下"的噪音 | 02 §1 |
| D-05 | 孩子端固定四分区，顺序为 需修改 → 要做的 → 等确认 → 已完成（折叠） | 需修改是唯一"被要求"且带动作的分区，压底会被反复滑过而不动手 | 01 §2.2、02 §2.2 |
| D-06 | **【自检修正】往期未完成任务并入「要做的」区承载**，带灰色「补交」标签，最多 3 条，其余折叠 | **自检时发现的真实缺口**：若今日任务页只显示当天任务，昨天未完成的任务会从界面消失，孩子找不到入口，"允许补交"这条冻结规则等于失效。此为本次交付中唯一影响功能完整性的修正，已同步修订 01/02/03/05 四份文档 | 01 §2.2.1、02 §2.2/§4、IR-01 前置、05 §3.2/§3.5 |
| D-07 | 「需修改」用紫色，不用橙、不用红 | 橙与星星黄冲突、易混；红色会把"再改一下"变成"做错了"。紫色表达"再来一次"，无惩罚联想 | 04 §2.2/§2.4 |
| D-08 | 家长端 Tab 角标用主色圆点，不用红色 | 红色在本产品语义中保留给"删除/覆盖"这类危险动作，角标只是待办数量 | 04 §7.6 |
| D-09 | 不做批量通过 | 若可一键通过全部，"只有家长审核通过才加分"退化为橡皮章；且一次误点后果不可逆（IR-09 不支持撤销） | IR-08 |
| D-10 | `approved` 为终态，不提供撤销；点错了走反向流水补偿 | 撤销需回滚任务状态、积分流水、宠物经验、连续记录四处，其中连续记录按日期聚合，回滚易产生空洞 | IR-09 |
| D-11 | 兑换**不冻结**余额；确认时校验，余额不足则降级为拒绝 | 冻结会让星星"看得见用不了"，对小学生比"申请没成功"更难理解。这是一次明确取舍，已在 IR-11 备案 | IR-11、02 §2.8 |
| D-12 | 手动调整积分**不影响**宠物经验与连续记录 | 经验与连续是"学习行为"的度量，手动调整是"家务对账"工具，混用会让度量失效 | IR-12 |
| D-13 | 备份提醒分四级（≤7 / 8–14 / ≥15 或从未 / 未持久化），只在家长端首页吸顶，可关当次不可永久关闭 | 这是无后端方案下唯一的数据保命提示；允许永久关闭等于允许用户丢掉全部记录 | 02 §7、IR-19 |
| D-14 | 连续页用"7 个圆点"而非图表，并明确写明"不算趋势图" | 圆点无坐标轴/网格/刻度，是打卡痕迹不是数据图表；而且折线会引入"跟你上周比"的比较心理 | 02 §2.4、IR-20 |
| D-15 | 导出全家庭所有孩子，不做单孩导出 | 单孩导出会让家长误以为已完整备份 | IR-17 |
| D-16 | 删除孩子保留其历史任务 | 删任务会让流水与历史记录断链，且家长事后可能想不起来删了什么 | IR-29 |
| D-17 | 恢复码 12 位、分组显示、全屏不可关闭弹层、强制勾选"我已抄写好了"才能继续 | 恢复码是家长 PIN 遗忘后的唯一出路，而它只显示一次。不强制确认，丢码率会很高 | 02 §8.1 |
| D-18 | PIN 使用自绘数字键盘，不调起系统键盘 | 系统键盘在平板上遮挡输入区，且带输入法联想，不适合纯数字场景 | 04 §7.7 |
| D-19 | 布局基准 375px，平板/桌面内容最大宽 720px 居中 | 手机为主场景（K2）；720px 是可读性上限，再宽会让孩子视线跨度变大、家长读表困难 | K2、05 §5 |
| D-20 | 星星余额用流水求和（派生），不存可写 balance 字段 | 存独立余额必然与流水不同步，一旦不一致就无法判断"谁对" | 05 §2.3 |

## 4. 逾期任务折叠：最终设计

### 4.1 折叠提示文案（规定措辞，不得改写）

| 状态 | 文案 | 条件 |
|---|---|---|
| 折叠态 | **`还有 N 条逾期任务，展开查看`** | N ≥ 1 时**必须出现**；N 为被折叠条数（总数 − 已展示 3 条） |
| 展开态 | **`收起`** | 展开后该行文案替换为"收起" |

**硬要求**：禁止只显示 3 条而让其余静默消失。折叠的代价必须用这一行换回来——**视觉压力可以降低，可发现性不能降低**。

### 4.2 展开入口位置

| 项 | 最终设计 |
|---|---|
| 位置 | 「要做的」区**底部最后一行**（不是标题旁、不浮动、不吸底） |
| 尺寸 | 通栏整行可点，高 48px |
| 样式 | 左对齐灰色文字（`--ink-500`，14px）+ 右侧下/上箭头；无背景、无描边、无阴影 |
| 为什么不放标题旁 | 区高约 500px，手机上滚到区中部时标题已出屏；入口在标题旁等于"滑到下面就找不到"。放在区末符合线性阅读的终点 |
| 为什么不用吸底浮动按钮 | 孩子端已有底部 Tab Bar，再叠一个浮动按钮会造成两个"底部固定元素"打架，且会遮挡最后一张任务卡 |

### 4.3 交互方式

| 动作 | 行为 |
|---|---|
| 点击折叠行 | 展开全部往期任务，200ms 高度过渡；行文案变「收起」 |
| 再次点击 | 收起，回到 3 条 |
| 跨页 | 切到宠物页/连续页再回来，保持上次展开状态（会话内记忆，键 = 孩子 ID + Tab） |
| 冷启动/刷新 | 恢复默认折叠（不持久化） |
| 点击任务卡 | 正常提交，与展开状态无关 |

### 4.4 折叠与数据的关系（最容易出错的一处）

| 项 | 规定 |
|---|---|
| 实现层位置 | **必须在渲染层切片**：查询取全部往期任务 → 渲染时切前 3 条 + 折叠行。**不得**在查询里 `limit(3)`（否则 N 算不出来，还容易连带限制 P-P3 取数） |
| 是否落库 | 不落库。禁止出现 `isCollapsed` / `hiddenByFold` 之类字段 |
| 是否影响查询 | 不影响。P-P3 只按"状态 = 待确认"取数 |
| 是否影响导出 | 不影响。导出必须包含被折叠的任务 |
| 违规后果 | 家长漏审 → 任务永久停在"等确认" → 孩子反复看到"已交，等确认"却永远等不到结果 |

### 4.5 家长端是否能收到折叠区里的提交

**能，而且必须有保证。**

| 环节 | 设计 |
|---|---|
| 孩子提交 | 折叠区内的任务与今日任务走同一个 `child.task.submit`，状态变 `submitted` |
| 家长端取数 | P-P3 查询条件 `状态 = submitted`，**不读任何折叠/逾期标记** |
| 列表呈现 | 该提交正常出现，同组、同优先级、同按钮，仅多一个灰色「补交」标签 |
| Tab 角标 | 计入待确认数（角标只数"待确认"，与补交无关） |
| 一句话 | **折叠只发生在孩子端的画面上，不发生在数据里。** |

### 4.6 视觉区分（补交 vs 当天）

| 维度 | 补交任务 | 当天任务 |
|---|---|---|
| 标签 | 灰色胶囊「补交」（`#F1F2F4` 底 / `#5C6370` 字，12px） | 无标签 |
| 副标题 | 「昨天的」/「11月16日的」 | 「每天」/「今天」 |
| 卡片样式 | 与当天任务**完全一致** | — |
| 主按钮 | 一致（「我做完啦」） | — |
| 禁止 | 红色、感叹号、逾期天数倒计时、"你迟到了"类措辞 | — |

### 4.7 完整提交流程（不打折）

```
补交任务（灰色「补交」标签）
   → 孩子点「我做完啦」
   → submitted（待家长确认）
   → 家长在 P-P3 看到（带「补交」标签）
   → 通过 → 单事务：状态 + 全部原定星星 + 等额经验（1:1）+ 连续记录记"今天"
   → 或 退回 → revision → 孩子可再次提交
```
**不简化流程、不跳过审核、不降低奖励、不追认原定日期的连续记录。**

## 5. IndexedDB 不可用时的具体界面行为

### 5.1 结论

> **阻止进入业务界面，不降级为"只读提示"。**

这是本轮被明确要求给出结论的一项，因此给出唯一答案，不留"可选方案"。

### 5.2 为什么不能做成只读降级（三条理由）

| # | 理由 |
|---|---|
| 1 | **技术上没有可读内容**。数据库打不开 = 一条记录都读不到，所谓"只读模式"只会渲染出一个全空界面（0 个孩子、0 条任务、0 颗星星） |
| 2 | **空界面比报错更伤信任**。家长看到"朵朵 0 颗星星、没有任何任务"，第一反应是"数据被清空了"，而不是"数据库打不开"。这会直接引发恐慌，并可能促使他做错误补救（导错文件覆盖） |
| 3 | **只读态没有产品价值**。提交、审核、兑换全依赖写入；一个只能看空列表的孩子端，比一句明确的"打不开"更没意义 |

### 5.3 三档分级

| 子场景 | 判定 | 行为 |
|---|---|---|
| **E3-c1 数据库无法打开**（被浏览器阻止、损坏、多标签页版本冲突） | 打开动作抛错 | **阻止进入** → 全屏数据异常页（见 5.4） |
| **E3-c2 可打开但个别读取失败** | 打开成功、查询抛错 | 降级为**该页错误卡** + 重试（E1）；保留 Tab Bar，其他页可用，**不清空界面、不跳全屏页** |
| **E3-c3 可打开但写入事务失败** | 写入抛错 | 按 E2：回滚到操作前、按钮恢复、提示重试（IR-33） |

### 5.4 全屏数据异常页规格

| 元素 | 内容 |
|---|---|
| 图标 | 中性灰文件图标（**不用红色感叹号**） |
| 主标题 | 「数据好像打不开了」 |
| 副文案 | 「你的记录应该还在，只是现在读不出来。先试试重新打开，不行可以从备份恢复。」 |
| 按钮 1（主） | 「重新打开」→ 重新加载应用 |
| 按钮 2（次） | 「从备份恢复」→ 直接进入导入流程（**必须允许在无数据库状态下选择文件**——这是用户唯一出路） |
| 按钮 3（弱） | 文字入口「关掉其他标签页再试」+ 说明「同时开多个页面有时会打不开」 |
| **禁止** | ❌ 显示 Tab Bar（不允许切到任何业务页）❌ 显示"0 个孩子 / 0 颗星星"的空数据 ❌ 提供"清空数据重来"（等于引导销毁证据）❌ 红色错误页 ❌ 技术错误码 |

### 5.5 另外五类场景（完整表已写入 `02` §8.2）

| 场景 | 行为一句话 |
|---|---|
| 正常离线使用 | 功能完全可用，**不显示任何网络提示** |
| 首次访问无缓存 | 明确提示需联网首次打开，不进入业务界面 |
| SW 缓存不可用 / 资源加载失败 | 提示"页面没加载完整" + 重新打开，**不归因为网络错误** |
| 存储空间不足 / 写入失败 | 回滚 + 可见提示 + 引导导出 + 备份提醒升 L2，**不静默失败** |
| PWA 安装 / 版本更新 | 安装入口只在 P-P5；更新提示"下次打开生效"，不强制刷新 |

**并额外落下一条产品级红线（`02` §0 与 §8.4）**：不得宣传"离线可用 = 数据不会丢"。离线只解决"能不能打开"，数据安全只由"持久化 + 导出备份"保障。凡是提到"本地很安全"的地方，必须同时出现"记得定期导出"。

## 6. 从"数据库无法打开"到"恢复成功"的完整流程

```
I3/I4 全屏异常页
  → ① 选文件（无需数据库）
  → ② 临时内存读取 + 七项校验（B1–B7 任一不过 → 换文件闭环，库不动）
  → ③ 恢复摘要 + 二次确认（"这会重建本机数据库"）
  → ④ 重建目标库 ──失败──▶ F3 终止态
  → ⑤ 单事务写入全部数据 ──失败──▶ F2 恢复中断
  → ⑥ 五项校验 ──不符──▶ F2
  → ⑦ 写"上次恢复时间"（不动"上次导出时间"）
  → ⑧ 重新加载
  → ⑨ 进入业务界面 + 一次性提示"已从 X 月 X 日的备份恢复"
```

**五条成功判据**（缺一即失败）：写入无异常 / 库能重新打开 / 各分区数量一致 / 关键值一致（星星合计=流水和、等级经验一致、连续记录条数一致）/ 抽样记录字段完整。

**必须写清的一点**：恢复不是"选中文件就算成功"。选文件只是第 ① 步；直到第 ⑥ 步五项全过，才有资格显示「恢复好了」。

## 7. "重建数据库仍失败"的终止态设计

| 项 | 内容 |
|---|---|
| 触发 | **仅**第 ④ 步重建目标库失败（浏览器禁用存储、隐私模式、策略限制） |
| 定性 | **环境问题，不是文件问题** |
| 标题 | 「这个浏览器现在用不了本应用」 |
| 正文 | ①"不是备份文件的问题——文件已经检查过了" ②"你的备份文件还在，换一个浏览器或设备，再用同一个文件恢复就可以" |
| 提供 | 可折叠诊断信息（环境、失败阶段、错误类别、时间、版本）、`复制诊断信息`、弱按钮"可能是什么原因？" |
| 不提供 | ❌ 重试主按钮 ❌ 自动重试循环 ❌ "恢复成功/部分成功" ❌ "先用空数据" ❌ 删除备份文件指引 |
| 为什么不做重试 | 同一环境重试必然再失败；给了按钮等于给假希望，还会让人反复点 |

## 8. 从"备份文件校验失败"到"重新选择文件"的失败闭环

## 7. 本轮是否新增 K / IR 编号

| 类型 | 结论 | 理由（不新增会漏什么） |
|---|---|---|
| **K 编号** | **未新增**（仍为 K1–K21） | 删除规则全部落在 IR-41 一条内即可表达。K 是"全域硬约束"，而删除只涉及 1 个入口 + 1 条流程；把它升成 K 会让 §5 约束表继续膨胀，反而不利于查阅。**但改了一条既有 K**：K18 补入"删除全部家庭数据"作为第三条数据消失路径——**不改会漏**：K18 原文说"数据消失只能由导入覆盖或删除孩子触发"，与新增的 G-05 直接矛盾 |
| **IR 编号** | **新增 1 条：IR-41（删除全部家庭数据）** | 不新增会漏：IR-16 是"导入=覆盖恢复"，与删除共享"数据会消失"这一表象但目的相反。若塞进 IR-16，实现时必然共用一套确认文案，家长分不清"找回"还是"清空"——这是本项目后果最重的误操作。另：删除有独立的 6 态界面与三档失败语义，需要独立条款承载 |
| 其他编号 | 未新增 V2-05 等 | G-05 尚未被判定为"第一版不做"，此时登记为候选会给 V2 规划制造虚假结论 |
| 交叉引用 | 未引入新编号体系 | `02` §8.7 用 `DEL-1～DEL-6`、`05` §3.11 用 `del_*` 状态名，均限定在各自文档内部，不与 K/IR 体系混用 |
