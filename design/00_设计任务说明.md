## 1. 项目目标（一句话）

给一个家庭里的多个小学生，提供一个**家长能统一管理、孩子自己能独立使用**的学习任务与激励工作台。

拆开看是三个约束，缺一不可：

- **家长统一管理**：一个家长模式，管所有孩子，不用来回切换账号。
- **孩子独立使用**：小学生不需要家长在旁边教怎么点。
- **激励而非监督**：产品情绪是"陪你变厉害"，不是"检查你有没有偷懒"。

## 2. 核心闭环（一句话）

> **家长布置任务 → 孩子完成 → 孩子提交 → 家长审核 → 积分到账 → 宠物成长 → 连续学习记录更新。**

这条链路上只有一个"真相时刻"：**家长点击"通过"的那一瞬间**。在它之前，星星（积分）、宠物经验、连续天数一律不变；在它之后，四者必须同时变，不允许只变一部分。

设计上的直接推论：孩子端的"我做完啦"**不是**得分动作，只是把球踢给家长；孩子端任何界面都不得提前显示"你即将获得 +10 星星"这类预期收益。

## 3. 设计范围

本版共设计 **9 个页面**：孩子端 4 页 + 家长端 5 页。页面数量与 `PRD_v1.3.md` 的页面清单一致，不增不减。另有 **1 个全局兜底层**（数据库异常与备份恢复界面，见 `02_页面状态矩阵.md` §8.5–8.7），它不属于 9 个业务页面，也不计入页面数。

### 3.1 孩子端（4 页）

| 编号 | 页面 | 页面性质 | 核心目的 | 对应闭环环节 |
|---|---|---|---|---|
| P-C1 | 身份选择 | 入口门（非常驻） | 让孩子在一屏内找到自己 | 进入闭环 |
| P-C2 | 今日任务 | 常驻 Tab 1 | 知道现在要做什么，并把它交出去 | 完成 / 提交 |

### 3.3 双端结构差异（设计要点）

- **孩子端 = 入口门 + 3 个 Tab**。身份选择不是 Tab，是每次冷启动的守门页；进去之后只有 3 个平级 Tab。
- **家长端 = 4 个 Tab + 1 个工具页**。设置与备份不是 Tab（它不是高频动作），从右上角齿轮进入，避免占据孩子的注意力位。

### 4.2 容易混淆的边界：宠物"成长 + 简单装扮"设计，复杂"养成系统"不设计

这一条必须写清楚，否则最容易越界：

| | 设计 | 不设计 |
|---|---|---|
| 宠物 | 一个固定形象、等级数字、经验条、升级反馈，以及帽子 / 眼镜 / 围巾 / 服饰 / 背景五类系统内嵌 SVG 装扮 | 喂食、饥饿值、心情值、道具、复杂宠物商店、上传素材、图片编辑器、进化分支、宠物对话、多宠物 |
| 装扮逻辑 | 孩子申请、家长确认后进入对应孩子收藏；已拥有才可正式穿戴；穿戴 / 卸下不扣分，刷新后保留 | 真实支付、装扮交易、库存、复杂动画、通过装扮改变经验或等级 |
| 成长逻辑 | 经验只来自"家长审核通过"这一事件；与星星由同一次事件触发、按同一发放系数派生（**当前建议 1:1，Q-05 待确认**），但**分开记账、互不派生**（K11） | 任何需要孩子额外操作才能维持的宠物状态；装扮兑换写 `petProgress` |

**判定口诀**：宠物是"进度可视化载体"，装扮只是外观收藏，不是"要照顾的第二个任务"。任何要求孩子"每天必须喂一下否则掉状态"的设计，都违反本条。

## 5. 设计约束（硬约束，不可自行放宽）

| 编号 | 约束 | 对设计的具体影响 |
|---|---|---|
| K1 | 中文界面 | 所有文案中文，不出现英文按钮、不做 i18n 占位。 |
| K2 | 双端适配，**手机为主、电脑补充** | 所有布局以 375px 宽为第一基准设计，再向上适配到平板/桌面（最大内容宽 720px 居中）。不做"桌面版压缩成手机版"。 |
| K3 | PWA | 必须可安装、可离线打开；设计需考虑"安装引导"和"版本更新提示"两个轻量场景，但不新增页面。 |
| K4 | 无业务后端 | 所有数据只在本机。界面不得出现"正在同步""云端已保存""其他设备"等措辞。**"保存成功"必须说成"已保存到这台设备"**。 |
| K5 | 家长 PIN 是儿童误触屏障，**不是安全锁** | 文案与视觉都不得暗示加密保护。禁止出现"安全""加密""保护您的隐私""防破解"。正确措辞方向："防止小朋友误点"。 |
| K6 | 孩子身份 = 头像 + 昵称 + 可选 PIN | 头像用固定可选集合（图形/动物），不做拍照上传。孩子 PIN 可选、可为 4 位数字。 |
| K7 | 任务四状态 | 待完成 / 待家长确认 / 已通过 / 需修改。状态名称与顺序不得改动，不得新增第五种状态。 |
| K8 | 逾期可补交（**全局允许**） | 逾期不是错误，是"晚了一点"。视觉上用灰色「补交」标签，**禁止红色警告、禁止"已逾期 X 天"的红色倒计时**。补交为全局规则，**不设按任务开关**；补交通过后获得该任务的全部原定星星，**但不追溯计入原定日期的连续记录**（Owner 决定 Q-04）。 |
| K9 | 只有家长审核通过才加分 | 见第 2 节。 |
| K10 | 积分是流水账本 | 界面只能展示流水与合计，**不提供"直接把星星数改成 80"的入口**。手动调整也必须生成一条带原因的流水。 |
| K11 | 宠物经验与积分**独立记录**（数据层已定）／**发放系数 1:1 待确认** | 两者在数据、流水与业务逻辑上完全分开：两套账、两条流水、两个更新入口，不得共用一个字段、不得由一方派生另一方。<br>**"1:1 发放"是设计建议（Q-05 待 Owner 确认），不是冻结规则。** 实现须把系数抽成常量（如 `EXP_PER_POINT`），不得把 1:1 写进业务判断，也不得在界面上向用户承诺"1 颗星星 = 1 点经验"。若 Owner 最终改为其他系数，只改常量，不动数据结构与界面结构。 |
| K12 | 奖励兑换需家长确认 | 孩子只能"申请"，不能自己兑换成功。 |
| K13 | 支持导出 / 导入 | 两个入口必须在家长端设置页显著可见，不得藏在三级菜单。 |
| K14 | 必须申请持久化存储 | 设置页需显示当前存储状态，并提供申请入口与失败说明。 |
| K15 | 必须有明显的备份过期提醒 | 家长端首页持续可见（分级见 `02_页面状态矩阵.md` 第 7 节）。 |
| K16 | 审核通过必须单事务原子完成 | 前端不得设计"先加分、再改状态、再涨经验"的分步动画。 |
| K17 | 连续学习按实际审核通过日期计算 | 补交只能记在"实际通过的那一天"，不得回填历史日期。当天尚未结束时不断言"中断"，跨过自然日之后才判定。**具体判定口径（今天/昨天/前天三档）是设计建议，Q-02 待 Owner 确认**，见 `03_交互规则.md` IR-20 与本文档 §9。界面上要能解释这一点。 |
| K18 | 历史数据永久保留（**已确认**） | 第一版**不提供历史日期回看入口**，但**不得因为没有回看入口而删除、自动清理或归档丢弃历史任务、积分流水、连续记录**。数据消失**只能**由家长主动的三种动作触发：①导入覆盖（IR-16）②删除某个孩子（删除孩子仍保留其历史任务，见 IR-29）③删除全部家庭数据（PRD §11.6 / IR-41，需验 PIN + 二次确认，属显式不可逆操作）。除这三种以外，无 TTL、无自动清理、无"仅保留 N 天"策略。 |
| K19 | 截止时间按本地自然日期（Owner 决定 Q-14，**已确认**） | `dueDate` 是**日期级**语义（如 `2026-11-19`），不是时间戳、不是日期时间字段。每日固定任务默认截止**当天 23:59**；临时任务可设置截止**日期**；第一版**不支持**小时/分钟级截止，不做时刻选择器。逾期与否一律按**设备本地自然日**比较（`dueDate < 今天`），不按 UTC、不按秒级时间差。 |
| K20 | 奖励无限量（Owner 决定 Q-13，**已确认**） | 奖励可有来源、分类、默认价 / 当前价、素材与快照等必要字段，但**无库存字段、无每人限兑字段、无库存扣减、无库存恢复、无"库存不足"文案**。兑换唯一的数值校验是**星星余额是否足够**。同一孩子同一装扮只收藏一份、已拥有后不再重复购买，是虚拟收藏去重，不是限量或限兑；生活奖励仍可重复兑换。不得把普通兑换写成"限量""仅剩 N 个""抢"或"已兑完"。 |
| K21 | 任务只有四状态，无放弃入口（Owner 决定 Q-15，**已确认**） | 四状态 = 待完成 / 待家长确认 / 已通过 / 需修改，**不得增加"已放弃""已过期""已取消"等第五状态**。孩子端**不设计**"我不想做了""放弃任务"入口。孩子确实做不到时，第一版仍走现有流程（保持待完成、或由家长退回/停用模板），不得为此新造状态或新流程。 |

## 6. 设计原则（小学生可用性）

1. **一屏一个主动作。** 每页只有一个主按钮，其他都是次要的。孩子不应该在三个同等重要的按钮之间犹豫。
2. **大。** 主按钮高度 56px 起，任务卡整卡可点，字号不小于 16px。手指比鼠标粗。
3. **图标优先，文字辅助。** 状态用"图标 + 颜色 + 文字"三重编码，不依赖单一通道（有色弱孩子）。
4. **无死路。** 任何空态、错误态、拒绝态都必须给出"下一步能做什么"，不允许出现只有一个"返回"的页面。
5. **不说教。** 全站禁止负罪感文案（"你又没完成""拖延""落后"）。需要修改说成"再改一下就好"，未完成说成"还没开始"。

| 项 | 内容 |
|---|---|
| 冲突来源 | `PRD_v1.3.md` §11.6「支持删除全部家庭数据：必须进入家长模式、必须验证家长 PIN、必须二次确认、明确提示删除后的影响、删除后不能留下可被误认为仍然有效的旧家庭业务数据」；§15.7 列为验收项。v0.3 设计无该入口 |
| 影响页面 | **P-P5 设置与备份**（新增一个危险操作分组）、删除后回到 **P-C1 空家庭 / 家长首次设置**；P-P1～P-P4 在删除后全部变空 |
| 影响数据模型 | 需要"清空全部业务表"的能力，且必须与"恢复备份"区分；删除后家长 PIN、恢复码、设置一并清除（否则会留下"旧家庭仍然有效"的错觉） |
| 影响备份文件 | **不影响、也不得删除**用户在设备文件系统上主动保存的备份文件（应用无权也不应触碰）；删除后用户仍可用旧备份恢复，这是需要说明的事实 |
| 需要 Owner 决定的问题 | ① 第一版是否**开放**这个入口（PRD 要求支持，Owner 可决定延后并记 V2）② 删除范围是否包含"家长 PIN 与恢复码"（本设计按"包含"）③ 删除后是否**强制跳回首次初始化并重设 PIN**（本设计按"是"）④ 是否允许"删除后立刻用旧备份恢复"（本设计按"允许但需重走恢复流程"，不做自动衔接） |
| 未裁决前的处置 | 设计已完整（`01` §3.5 / `02` §2.9、§8.7 / `03` IR-41 / `05` §3.9、§3.11），**Trae 可按设计实现**；若 Owner 否决，只需回退一个入口，不动数据模型（与 G-01 不同） |

**为什么 G-05 可以不阻塞**：它是"多一个入口/少一个入口"的取舍，删除能力在任何版本都要有（家长换设备或送人时需清空），成本集中在一条流程内、回退代价低。**G-01 不同**：它决定数据模型里有没有 Blob，一旦按"无附件"建模完成再改，等于重建任务表与备份格式。
