## 0. 规则用法

每条规则采用统一四段式，其中「禁止」段是硬性红线，Trae 实现时不得偏离：

```
IR-XX 规则名
  触发 / 条件
  动作
  失败兜底
  禁止
```

规则编号在 `05_交接说明.md` 中被逐页引用，便于实现对照。

**决策状态标注（全文档统一，口径见 `00` §8）**：本文件每条规则后面可能出现三种标注，含义不同，不可混用——

| 标注 | 含义 | 实现方式 |
|---|---|---|
| **（已确认）** 或无标注 | D1：Owner 已决定，或 PRD 已冻结且未被推翻 | 必须照做，不得回退 |
| **（待 Owner 确认）/（D2）** | D2：方案完整可实施，但**未获批准** | 可按方案实现，但必须保留可换空间（常量、参数、不写死结构） |
| **（后续版本 / V2）** | D3：已判定第一版不做 | 不实现，也不得偷偷预留入口 |

当前 D2 项：IR-02（Q-03）、IR-20（Q-02）、IR-05 中的 1:1 系数（Q-05）、IR-41（G-05）、IR-03 的"无附件"口径（G-01）。**这些不是冻结规则**，QA 与 Owner 可随时改判。

## 1. 任务生命周期

### IR-01 任务的四状态流转（唯一合法路径）

```
         ┌──────────────┐
         │   todo       │  待完成
         │  待完成       │
         └───┬──────┬───┘
   孩子提交   │      │  家长退回后重新提交
             ▼      │
      ┌────────────┐│
      │ submitted  ││  待家长确认
      │ 待家长确认  ││
      └──┬──────┬──┘│
  通过    │      │    │退回
          ▼      ▼    │
   ┌──────────┐ ┌────────────┐
   │ approved │ │  revision  │──┘
   │ 已通过    │ │  需修改     │
   └──────────┘ └────────────┘
        （终态）
```

| 转换 | 触发者 | 前置条件 |
|---|---|---|
| `todo → submitted` | 孩子 | 任务属于该孩子、当前为 todo（**含往期未完成任务**，补交即由此进入） |
| `submitted → approved` | 家长 | 家长模式已通过 PIN |
| `submitted → revision` | 家长 | 必须填写或选择退回原因 |
| `revision → submitted` | 孩子 | 当前为 revision |

**禁止**：
- ❌ 任何"跳过 submitted 直接 approved"的路径（包括家长"我替他点完成"）
- ❌ `approved` 回退到任何状态（见 IR-09）
- ❌ 新增第五种状态（如"已过期""已放弃""已取消"）
- ❌ 孩子端的"放弃任务 / 我不想做了 / 跳过这条"入口（Owner 决定 Q-15：第一版不支持主动放弃）。孩子做不到时，任务**保持 `todo`**，不催、不罚、不自动失效；家长侧可用"停用模板"阻止后续生成，但不得因此删除已生成实例或历史记录
- ❌ `revision → todo`（退回必须留在 revision，否则孩子会以为任务没做过）

### IR-02 每日/每周任务的实例化

| 项 | 规则 |
|---|---|
| 触发 | 应用打开时（P-C1 或任意页首次进入），按当天日期检查 |
| 条件 | 存在生效中的「每日」模板 → 为每个适用孩子生成当天实例。<br>「每周」模板 → **只在其指定的星期生成**；星期为**必填、可多选**（如周一 + 周三 + 周五），未指定星期的周模板不允许保存。<br>⚠️ **星期规则是设计建议（Q-03 待 Owner 确认，见 `00` §9）**：方案已可直接实现，但不得视为冻结规则 |
| 动作 | 生成 `todo` 状态实例；**已存在同日同模板实例时不重复生成**（幂等） |
| 失败兜底 | 生成失败不阻断进入应用；下次打开重试；家长端 P-P1 若发现今日实例缺失，显示一行浅灰提示「今天的任务还没生成，下拉重试」 |
| 禁止 | ❌ 补生成历史日期的实例（错过的日子不补）❌ 修改模板后回改已生成的当天实例 ❌ 允许"每周"模板在未选星期的情况下保存 ❌ 允许"每周"退化为"每天都生成"（不选星期 ≠ 全周生效） |

### IR-02b 截止时间的语义（日期级，Owner 决定 Q-14）

| 项 | 规则 |
|---|---|
| 语义 | `dueDate` 是**本地自然日期**（如 `2026-11-19`），不是时刻、不是时间戳 |
| 默认值 | 每日固定任务：生成当天实例，默认截止**当天 23:59**（表示为"当天"这一日期，不存 23:59 这个时刻） |
| 临时任务 | 家长可设置截止**日期**；不提供小时/分钟选择器 |
| 逾期判定 | 一律按"设备本地自然日"比较：`dueDate < 今天` 即逾期。**不**用 UTC、**不**用秒级时间差、**不**做时区换算 |
| 边界情况 | 家长把临时任务设成"今天"→ 今天之内提交都算按时；设为"昨天"→ 立即带「补交」标签但**不阻止提交**（Q-04 全局允许补交） |
| 禁止 | ❌ 把 `dueDate` 改成时间戳或日期时间字段 ❌ 引入"晚 8 点前"这类时刻规则 ❌ 用 `new Date()` 的时分做逾期判断 ❌ 因逾期把任务置灰不可点 |

### IR-03 孩子提交（"我做完啦"）

| 项 | 规则 |
|---|---|
| 触发 | 孩子在 P-C2 点某张 `todo` 或 `revision` 卡片的主按钮 |
| 动作 | ①按钮立即禁用并显示「交上去啦…」②写入 `submitted` + 提交时间戳 ③成功后卡片原地变为"等爸爸妈妈看"态 ④不跳页、不弹窗 |
| 失败兜底 | 事务失败 → 按钮恢复可点 + 顶部一条提示「没交上去，再点一次」；状态保持原样 |
| 禁止 | ❌ 提交后允许孩子撤回（撤回意味着孩子可以反复改，破坏"提交即锁定"的约定）❌ 一次点击提交多条任务 ❌ 提交时增加任何附加表单 |
| **关于"附加表单"的边界（G-01，待裁决）** | 本基线当前口径是"提交 = 点一下"，**不含文字/照片输入**。但这**不是冻结规则**：`PRD_v1.3.md` §5.3 要求支持文字提交与照片提交，Owner 尚未裁决（`00` §9.1）。若裁决包含，本条的"禁止"仅保留"不得一次提交多条"与"不得撤回"，附件输入按新规格补；**在裁决前，Trae 不得自行实现拍照上传，也不得把"无附件"写进数据模型的不可逆假设里** |
| **不可动摇的一条** | 无论提交方式如何扩展，**提交只改变任务状态（→ 待家长确认），不发放任何奖励**。任何"孩子自己确认一下就到账"的路径都违反 IR-05 |

### IR-04 提交后锁定

| 项 | 规则 |
|---|---|
| 规则 | `submitted` 状态下，孩子端该任务**完全只读**：无任何按钮、不可编辑任务名、不可补写内容 |
| 唯一解锁条件 | 家长退回（→ `revision`） |
| 失败兜底 | 不适用（无操作） |
| 禁止 | ❌ 提供"我要改一下"的撤销入口 ❌ 提供"再提交一次"（重复提交会产生两条待确认记录） |

## 2. 审核（核心规则区）

### IR-05 审核通过是原子动作

| 项 | 规则 |
|---|---|
| 触发 | 家长在 P-P3 点「通过」 |
| 前置 | ①家长模式已验证 ②该任务当前为 `submitted` ③该任务未被其他操作占用 |
| 动作 | **单事务内一次性完成四件事**：<br>①任务 `submitted → approved`（写审核时间、审核人）<br>②新增一条积分流水（`+N 完成「任务名」`）<br>③宠物经验 +N 并处理升级<br>④重算该孩子连续学习记录（按**今天**，不按任务应完成日）<br>事务提交成功后才更新界面。 |
| 界面更新方式 | 事务返回后**一次性刷新**：卡片消失 + 轻提示 + （若孩子正在宠物页）经验条推进。**不分步、不预演、不乐观更新** |
| **事件幂等键** | 每一次审核通过事件使用 **`approval:${taskId}`** 作为幂等键。同一任务重复触发时必须被识别为同一次事件，**不得产生第二条积分流水、第二条经验流水、第二次连续记录写入**。键的唯一性约束应落在数据层（唯一索引或事务内存在性校验），不能只靠 UI 禁用 |
| 失败兜底 | 事务失败 → **四项全部不变**，卡片恢复原状，顶部提示「这次没成功，再点一次」 |
| 禁止 | ❌ 「先加分 → 再改状态 → 再涨经验」的分步动画 ❌ 乐观更新（先改 UI 再等结果）❌ 在事务外分别调用三个独立写入 ❌ 审核成功但连续记录未更新 ❌ 不使用幂等键（重复触发会产生重复流水） |

**给 Trae 的实现提示（非强制技术方案）**：这四项必须在同一个 Dexie `transaction` 内完成。若事务跨越多个 store，请确保 store 列表完整声明，避免 Dexie 因未声明 store 而抛出隐式事务错误。

### IR-06 防重复点击

| 项 | 规则 |
|---|---|
| 触发 | 点击「通过」或「需要再改一下」的提交按钮 |
| 动作 | ①按钮立即 `disabled` ②显示「确认中…」③**该卡片上所有操作按钮同时禁用** ④直到事务返回（成功或失败）才恢复或移除 |
| 时间下限 | 即使事务在 20ms 内返回，禁用态也需保持 ≥ 300ms，避免视觉闪烁让孩子/家长以为没点上 |
| 二次保护 | 除 UI 层禁用外，写入时必须以任务 ID + 当前状态做条件更新（只有状态仍为 `submitted` 才写入），并配合幂等键 `approval:${taskId}`（IR-05）；若条件不满足则视为"已被处理"，UI 提示「这条已经处理过了」并刷新列表 |
| 禁止 | ❌ 仅靠防抖（debounce）而不禁用按钮 ❌ 事务未返回就允许再次点击 ❌ 失败后自动重试（重试必须由人触发） |

### IR-07 退回必须给理由

| 项 | 规则 |
|---|---|
| 触发 | 家长点「需要再改一下」 |
| 动作 | 弹出原因弹层：4 个预设（`字写得不够清楚` / `还没写完` / `再检查一遍` / `下次注意时间`）+ 自由填写（≤50 字） |
| 必填校验 | 预设与自由填写至少选/填一项，否则「确认退回」禁用 |
| 成功后 | 孩子端该卡片直接展开显示原因文本（见 02 文档 5.3） |
| 禁止 | ❌ 允许无理由退回（孩子收到"需修改"却不知道为什么，会产生无力感）❌ 退回原因使用指责性措辞（预设项已规避）❌ 退回原因字数超过 50 字（会破坏卡片布局，且长文本等于变相批评） |

### IR-08 批量审核

| 项 | 规则 |
|---|---|
| 结论 | **不做批量通过。** |
| 理由 | 产品前提是"只有家长审核通过才加分"。批量通过会让审核退化为一次点击的橡皮章，同时放大了误操作后果（一次误点通过 10 条，且无法撤销）。 |
| 允许的简化 | P-P3 的列表支持"连续处理"：通过一条后焦点自动落到下一条，家长可以用手指连续点，但每条仍是独立事务、独立确认。 |

### IR-09 审核通过不可撤销

| 项 | 规则 |
|---|---|
| 结论 | `approved` 是终态，界面上**不提供**撤销/反审核。 |
| 理由 | 撤销意味着要回滚积分流水、宠物经验、连续记录三处数据，且连续记录是"按日期"聚合的，回滚容易产生历史空洞。产品选择"不撤销"，用"确认前看清楚"来替代"事后改错"。 |
| 补偿通道 | 若家长确实点错了，走 **IR-12 手动调整**：用一条带原因的负向流水把星星扣回，宠物经验不可逆（视觉上承认"经验留着"），连续记录保留（当天确实有任务通过）。 |
| 禁止 | ❌ 提供"撤销"按钮 ❌ 提供"编辑已通过记录" |

## 3. 积分与兑换

### IR-10 积分账本只增不改

| 项 | 规则 |
|---|---|
| 规则 | 星星余额**不是**一个可编辑的数字，而是流水求和的结果。界面只展示"合计"，任何变更都必须新增一条流水。 |
| 流水必要字段 | 时间、变动值（正/负）、事由文案、来源类型（完成 / 兑换 / 手动调整） |
| 禁止 | ❌ 提供"设置星星数为 X"的输入框 ❌ 删除历史流水 ❌ 修改已生成流水的金额（错了只能用反向流水冲正） |

### IR-11 奖励兑换：申请 → 确认 → 扣分

| 阶段 | 执行者 | 动作 | 数据变化 |
|---|---|---|---|
| ① 申请 | 孩子 | 在 P-C3 点「我想换这个」 | 校验奖励启用、属于当前孩子操作且该孩子无其他 pending；装扮还须未拥有。写入 `pending` 及奖励名称 / 价格 / 类别快照，装扮另存 costumeKey / assetKey 快照。**不扣分、不冻结、不写流水** |
| ② 确认 | 家长 | 在 P-P4 点「确认」 | 只处理 `pending`，按**价格快照**重新汇总当前孩子流水并复核余额。单事务写负向流水（`source=redeem`、关联 redemptionId）+ `accepted` / handledAt；装扮同事务写入该孩子收藏 |
| ② 拒绝 | 家长 | 在 P-P4 点「拒绝」 | 只处理 `pending`，状态改 `rejected` + handledAt，可写 ≤30 字家长留言；**不扣分、不产生流水、不发装扮** |

| 关键规则 | 内容 |
|---|---|
| 状态机 | 只有 `pending → accepted` 与 `pending → rejected`。两者均为终态；accepted 不可再拒绝或确认，rejected 不可再确认 |
| 不做冻结 | 申请时不预扣、不锁定余额；申请时余额不足不阻止提交。孩子申请后仍可继续赚星星，余额仍在变 |
| 快照优先 | 审核列表展示名称与价格快照；确认金额只取申请快照。家长之后改名、改价或停用奖励，不回改 pending / 历史申请。停用只阻止新申请，已有 pending 仍可确认或拒绝 |
| **不做库存（Owner 决定 Q-13）** | 不设库存、扣减 / 恢复库存或"每人限兑 N 次"。兑换唯一的数值校验是**星星余额是否足够**。不得出现"限量""仅剩 N 个""抢完了""已兑完"；两个孩子在同一天换同一奖励都成立 |
| 余额不足的处理 | 家长点「确认」时若当前余额 < 快照价格：**不允许成功、不写任何数据**，提示「现在只有 20 颗星星，换这个需要 30 颗」+「先不换了」；家长点击后 = 拒绝，不扣分，可选填一句说明 |
| 待确认唯一 | **同一孩子同一时间只允许 1 条 pending**，不是同一奖励一条。提交服务必须在事务内再次检查，不能只靠按钮禁用；已有 pending 时全部奖励按钮只读「等确认中」 |
| 重复申请 | 生活奖励完成后可再次申请。装扮已拥有后不再提供兑换入口，且写入时校验收藏唯一；这是收藏去重，不是库存或限兑 |
| 确认幂等 | 扣分流水建议 `eventKey = redemption:${redemptionId}` 且唯一。重复确认已 accepted 的申请只返回原处理结果，不新增流水或收藏；装扮收藏还需 `(childId, costumeKey)` 唯一 |
| 失败兜底 | 确认事务任一步失败，申请状态、积分流水、收藏全部不变，家长可重试。UI 不得先显示兑换 / 装扮到账再等待事务 |
| 多孩隔离 | 申请、余额汇总、审核、收藏和穿戴均以申请 / 当前选择的 childId 校验，禁止只凭 rewardId 或页面上一个孩子缓存写入 |
| 禁止 | ❌ 申请时扣分或冻结 ❌ 孩子端自行完成兑换 ❌ 拒绝时扣分 ❌ 自动通过 ❌ 负余额 ❌ 用奖励当前价覆盖申请快照 ❌ 增加库存 / 限量 / 限兑 ❌ 装扮兑换写 petProgress 或改变等级 |

**这个设计承认的取舍**：不冻结意味着存在"申请时够、确认时不够"的竞态。我们选择在确认时校验余额并由家长降级为拒绝，而不是在申请时锁定余额——因为冻结会让孩子的星星"看得见用不了"，对小学生更难理解。

### IR-11A 奖励配置：模板默认价不覆盖家庭当前价

| 项 | 规则 |
|---|---|
| 内置模板 | 系统目录保存稳定 templateKey、名称、类别、素材与建议默认积分；首次启用 / 初始化时创建家庭奖励配置，`defaultCost` 与 `cost` 取建议值 |
| 家长改价 | 家长只修改本家庭奖励配置的当前 `cost`；之后的新展示 / 新申请使用当前价。默认价仅作建议对照，不是固定价格 |
| 初始化幂等 | 刷新、重进、重启、重复 Seed / 模板补齐按 templateKey 只补缺失配置；已有配置的 cost、enabled 和家长内容一律不覆盖 |
| 自定义奖励 | 仅创建生活奖励；名称、说明、系统内置图标、显式积分必填，不能自动继承模板价格。可编辑和启停，不在本版删除 |
| 历史保护 | 停用 / 编辑不删除申请、流水和收藏。不同本地家庭空间的配置独立，不回写系统模板 |

### IR-11B 宠物装扮：收藏、预览与穿戴

| 项 | 规则 |
|---|---|
| 到账 | 只有家长确认事务成功后才写入当前孩子收藏；pending、rejected 或事务失败均不到账 |
| 预览 | 未拥有可查看临时效果，但预览不保存为正式穿戴；未拥有不能正式穿戴 |
| 穿戴 / 卸下 / 切换 | 仅孩子管理自己的已拥有装扮；每个类别最多一件，同类别切换替换，不同类别可共存。操作不扣分、不写 pointLedger / petProgress |
| 持久化与隔离 | 收藏和当前穿戴按 childId 持久化；刷新 / 重进后保留。写入前同时校验 childId、costumeKey 和收藏归属，不能跨孩子穿戴 |
| 素材与动效 | 第一版只用系统内嵌 SVG（CSS 可辅助）；不上传、不编辑图片、不做复杂动画。升级仍是唯一庆祝动效 |
| 失败兜底 | 穿戴写入失败保持原正式状态并允许重试；预览状态不得被误当持久化状态恢复 |

### IR-12 手动调整积分

| 项 | 规则 |
|---|---|
| 触发 | 家长在 P-P4 点「手动调整」 |
| 表单 | ①选择孩子 ②变动值（+ / - 与数字，或快捷按钮 +5 / +10 / -5）③**原因（必填，≤30 字）** |
| 校验 | 原因为空时「确定」禁用；负向调整后余额不得为负数（若会为负，提示"最多只能扣 X 颗"） |
| 动作 | 单事务写入一条流水（来源类型 = 手动调整，附带原因文本） |
| 界面 | 流水列表中该条需**明显区别于任务完成**：显示 `手动调整` 灰色标签 + 原因文本 |
| 失败兜底 | 事务失败 → 弹层保留已填内容 + 提示重试 |
| 禁止 | ❌ 无原因的手动调整 ❌ 直接改合计数字 ❌ 静默调整（必须留痕） ❌ 手动调整影响宠物经验（经验只来自审核通过）❌ 手动调整影响连续记录 |

**为什么手动调整不影响经验与连续**：这两项是"学习行为"的度量，手动调整是"家务对账"的工具。混在一起会让度量失去意义。

|---|---|

| 禁止 | ❌ 把 PIN 存成"看起来加密"的形式并对外宣称安全 ❌ 用生物识别/系统锁替代 PIN（PWA 能力不稳定，且超出冻结范围）❌ 家长 PIN 用于数据加密 |

## 5. 数据安全

### IR-16 导入：二次确认 + 自动备份

| 阶段 | 规则 |
|---|---|
| 触发 | 家长在 P-P5 点「导入数据」并选择文件 |
| 前置校验 | 校验文件格式与版本标识；不通过则拒绝（见 02 文档 2.9 异常） |
| **二次确认** | 弹层明确写清三件事：<br>①「导入会**替换**现在的全部数据」（替换，不是合并）<br>②「当前有 3 个孩子、共 128 条任务记录」<br>③「导入前会自动备份现在的数据」<br>按钮：`取消` / `继续导入`（危险色，需再次点击确认，不做长按） |
| **自动备份** | 确认后**先**导出当前数据到本地一组记录（内部安全副本），成功后才执行导入。备份失败 → 中止导入并提示 |
| 执行 | 单事务完成替换；界面显示「正在导入…」 |
| 失败兜底 | 导入失败 → 回滚到导入前状态 + 用内部安全副本兜底 + 提示「导入没成功，数据还是原来的」+ 提供「导出这次的备份文件」 |
| 成功 | 「导入完成，一共 3 个孩子、241 条任务」+ 自动跳到 P-P1 |
| 禁止 | ❌ 无二次确认直接导入 ❌ 静默合并（合并会产生重复任务与错乱流水）❌ 导入前不备份 ❌ 导入覆盖时不告知将被覆盖的数据量 |

### IR-17 导出

| 项 | 规则 |
|---|---|
| 触发 | P-P5「导出数据」或备份提醒条「立即导出」 |
| 动作 | 生成一个本地文件（JSON），文件名含日期：`学习工作台备份_2026-11-19.json` |
| 成功后 | 记录"上次导出时间" + 轻提示「备份好了，文件已保存到你的设备」 |
| 内容说明 | 导出**全家庭所有孩子**的数据（不做单孩导出，避免家长误以为备份完整） |
| 二进制/照片 | 若数据中存在照片等二进制内容，**必须导出实际 Blob/二进制本体**，不得只存临时 URL、`blob:` 链接或 objectURL（那些在重开应用后全部失效）。<br>⚠️ **当前设计不含附件**（00 §7.2 G-01：PRD §5.3 要求文字/照片提交，本设计未含附件，待裁决）。一旦裁决支持照片提交，本条立即成为导出验收项；在此之前不得以"没有附件"为由删掉本条 |
| 禁止 | ❌ 提示"已上传""已同步" ❌ 导出时省略密码/PIN 相关信息导致无法恢复（导出应包含可完整恢复所需的一切） |

### IR-18 持久化存储申请

| 项 | 规则 |
|---|---|
| 时机 | ①首次进入家长模式时（一次，非阻断）②P-P5 存储状态区手动触发 ③检测到未持久化且已过 7 天 |
| 动作 | 调用浏览器持久化 API，按结果更新状态：已开启 / 未开启 / 被拒绝 |
| 展示 | P-P5 明确显示当前状态，用家长能懂的话：<br>已开启：「浏览器已承诺尽量保留数据」<br>未开启：「浏览器可能会在空间紧张时清掉数据」 |
| 被拒绝 | 不反复弹窗；改为在 P-P1 显示 L3 提醒（见 02 文档 7.1） |
| 禁止 | ❌ 用"安全""加密"描述持久化 ❌ 每次打开都弹申请 |

### IR-19 备份提醒的计算与关闭

| 项 | 规则 |
|---|---|
| 计算基准 | 上次成功导出的时间戳；从未导出视为"需要强提醒" |
| 阈值 | ≤7 天不显示；8~14 天 L1；≥15 天 L2 |
| 关闭 | 允许关闭当次（同一会话不再出现），**不允许永久关闭** |
| 归零 | 导出成功后立即重算并淡出 |
| 禁止 | ❌ 孩子端显示备份提醒 ❌ 提供"不再提醒"的永久开关 |

## 6. 连续学习

### IR-20 连续天数计算口径

| 项 | 规则 |
|---|---|
| 定义 | 连续天数 = 从"最近一次有通过记录的日期"向前，逐日连续、且每天至少有 1 条任务在该日被审核通过的天数 |
| 基准日 | **审核通过的实际日期**，不是任务应完成日期 |
| 补交处理 | 今天通过一条昨天应完成的任务 → 记在**今天**，昨天的格子不会亮（Q-04 不追溯） |
| **判定规则（设计建议，Q-02 待 Owner 确认，见 `00` §9）** | 设 `lastPass` = 最近一次有通过记录的日期，`today` = 今天：<br>① `lastPass == today` 或 `lastPass == yesterday` → **保留**当前连续天数（今天尚未结束，不得断言中断）<br>② `lastPass <= 前天` → 连续天数 = **0**，从今天重新计<br>③ 判定只发生在两个时机：**日期变更时**、**审核通过时**。不在界面停留期间随时间漂移（避免 23:59 打开着的页面突然归零）<br>⚠️ 本口径尚未获 Owner 批准：实现时请把判定收敛到一个纯函数（输入 lastPass / today / 当前值），**不要**把三档逻辑散落到多个组件里 |
| 展示（今天未完成、昨天已完成） | 显示保留的连续天数；今天圆点为空心态；**不加"今天还没完成"的提示、不加感叹号、不变灰、不闪烁** |
| 展示（跨日已中断） | 显示 0，文案为「今天是新的一天」，不出现"中断""可惜""归零"等词 |
| 展示 | P-C4 大数字 + 最近 7 天点阵 + 固定解释文案：「只有爸爸妈妈当天确认通过，这一天才会亮起来。」 |
| 禁止 | ❌ 回填历史日期 ❌ 显示"你已中断"的红色提示 ❌ 用百分比代表连续度 ❌ 显示最长记录（引入比较心理，且不在冻结范围）❌ 在页面停留时做"实时归零" |

**一个必须能算对的例子**（建议写成单元测试）：

```
周一~周六 每天都有通过 → 周日早上打开：连续 6 天（lastPass = 周六 = yesterday，规则①）
周日 全天无通过
周一 早上打开：连续 0 天（lastPass = 周六 = 前天，规则②），文案「今天是新的一天」
周一 通过 1 条 → 连续 1 天
```

|---|---|
| 规则 | 同一天通过多条任务，星星与经验累加，连续天数只算 1 天 |
| 界面 | 连续页当天圆点只显示一次点亮，点击可看到当天通过的全部任务 |

## 8. 逾期折叠与存储异常（R1 新增）

### IR-31 逾期任务折叠是纯 UI 状态，不得影响审核可达性

| 项 | 规则 |
|---|---|
| 定义 | 「还有 N 条逾期任务，展开查看」是**客户端展示层状态**，不属于任务数据 |
| 必须 | ① 折叠不写入任何持久化字段（不得出现 `isCollapsed` / `hiddenByFold` 之类落库字段）② 折叠不得作为任何查询、同步、导出的过滤条件 ③ 导出数据必须包含被折叠的任务 ④ 折叠状态仅在内存/会话存储中保留，冷启动恢复默认折叠 |
| 关键后果 | 孩子提交**折叠区内**的任务后，该任务立刻是 `submitted`，家长端 P-P3 的查询条件只有"状态 = 待确认"，因此**必然收到**。若实现时把折叠做成数据字段并参与过滤，家长会漏审，任务会永久停在"等确认"——这是本规则要防的唯一事故 |
| 折叠提示必须出现 | 被折叠条数 N ≥ 1 时，区底部必须显示 `还有 N 条逾期任务，展开查看`；展开后变「收起」。**禁止静默折叠**（只显示 3 条、不提示还有更多） |
| 失败兜底 | 不适用（无写入） |
| 禁止 | ❌ 折叠状态落库 ❌ 折叠影响 P-P3 / P-P1 的数据获取 ❌ 折叠影响导出内容 ❌ 折叠影响连续天数或任务统计 |

### IR-32 IndexedDB 不可用时阻止进入，不降级只读

| 项 | 规则 |
|---|---|
| 触发 | 打开数据库失败（被浏览器阻止、文件损坏、多标签页版本冲突） |
| 动作 | **阻止进入业务界面**，显示全屏数据异常页（规格见 `02_页面状态矩阵.md` 8.3）：标题「数据好像打不开了」+ 主按钮「重新打开」+ 次按钮「从备份恢复」+ 文字入口「关掉其他标签页再试」 |
| 必须 | ① 不渲染 Tab Bar ② 不渲染任何"0 个孩子 / 0 颗星星"的空数据界面 ③ 不提供"清空数据重来" ④ 允许在该状态下直接进入导入流程（因为用户此时唯一的出路是恢复备份） |
| 局部失败例外 | 若数据库可打开、仅个别读取失败 → 走 E1（页内错误卡 + 重试），**不清空界面、不跳全屏页**（细则见 IR-40） |
| 恢复路径 | 数据库打不开时，"从备份恢复"**不能依赖原数据库**，必须走 IR-36 的独立恢复流程（校验 → 确认重建 → 建库 → 写入 → 校验 → 重载）；该流程的失败与终止态见 IR-38 |
| 文案 | 必须包含"数据应该还在，只是现在读不出来"，避免家长误判为数据丢失而做错误补救 |
| 禁止 | ❌ 降级为"只读模式"并展示空数据（技术上无内容可读，且空界面比报错更伤害信任）❌ 显示技术错误码 ❌ 用红色错误页 ❌ 自动清库重试 ❌ 在异常页提供"清空重来" |

### IR-33 写入失败与空间不足不得静默

| 项 | 规则 |
|---|---|
| 触发 | 任意写入事务失败。**必须先分诊，再给文案**——三类失败的处置不同，不能一律说"网络问题"或"重试" |
| **分诊** | ① **事务性失败**（约束冲突、中止、并发条件不满足）：可重试；回滚后提示「这次没保存上，再点一次」<br>② **配额/空间不足**（`QuotaExceededError` 一类）：**重试必然失败**，不得鼓励反复重试；提示「手机空间不够了，先导出备份或清理一下空间，再试一次」，并引导去导出<br>③ **浏览器限制/策略拒绝**（隐私模式、禁用存储、策略收紧）：重试同样无效；提示「这个浏览器现在不让保存数据」，并引导换浏览器/退出隐私模式；若发生在启动阶段，落到 IR-38 的终止态 |
| 动作 | ① 按 IR-05 / IR-22 回滚到操作前状态 ② 顶部提示人话原因（按分诊结果）③ 引导「导出备份」④ 家长端首页备份提醒按级别升级（空间类升 L2） |
| 必须 | ① 失败必须可见，不允许 `catch` 后静默 ② 按钮/弹层恢复可操作 ③ 已填内容不丢失（表单类）④ 失败时**绝不**提前发放积分、经验或连续记录（不得先播成功动画再报错） |
| 降噪 | 同一会话内同类失败连续出现 3 次后，不再重复顶部提示，改为在家长端 P-P5 存储区常驻一条状态说明（避免每次操作都弹一次） |
| 禁止 | ❌ 静默失败 ❌ 无限自动重试 ❌ 对配额类失败反复提示"再点一次" ❌ 提示"网络问题" ❌ 提示"请联系客服"（无客服体系）❌ 在失败后仍显示成功态 ❌ 通过删除历史任务/流水来"腾空间" |

## 9. 数据库异常、备份恢复与删除全部数据（DEV-B002-003 新增 / R2 补 IR-41）

本节解决一个此前没写透的问题：**原数据库完全打不开时，"从备份恢复"到底怎么落盘？** 恢复不能依赖那个已经打不开的数据库。

### IR-34 恢复流程的总原则：恢复不依赖原数据库

| 项 | 规则 |
|---|---|
| 前提 | 恢复的入口有两种：① 数据库**打不开**的全屏异常页（IR-32）② 家长端 P-P5 正常导入（IR-16）。两者共用同一套校验与落盘规则，但**路径不同**：正常导入是在已有库上覆盖；异常恢复是在**没有可用库**的前提下重建 |
| 原则 1 | **读取与校验必须在数据库之外完成**：文件读取、JSON 解析、结构校验、版本校验、完整性校验全部在**临时内存（及临时存储）**中完成，此阶段不触碰任何业务库 |
| 原则 2 | **先校验、再动库**：校验不通过时，**不创建、不删除、不清空任何数据库**，直接返回失败并保留文件 |
| 原则 3 | **重建必须由用户明确确认**：只有校验通过后，才提示"需要重新初始化本地数据库"，由家长点确认；不得自动重建 |
| 原则 4 | **恢复是一次性交付，不是多次半成品**：要么恢复完整并校验通过，要么回到"未恢复"状态并明确告知，不允许留下"一半数据"的库 |
| 原则 5 | **原备份文件只读**：恢复过程中不修改、不移动、不删除用户选择的备份文件；恢复失败后该文件仍可再次使用 |
| 失败兜底 | 任一阶段失败 → 停在该阶段，给对应人话提示（见 IR-38），**不显示任何"恢复成功"的暗示** |
| 禁止 | ❌ 在数据库打不开时因"无法写入"而放弃恢复入口 ❌ 用"新建一个空库然后提示成功"冒充恢复 ❌ 校验未通过就开始重建 ❌ 恢复过程中删除用户的备份文件 |

### IR-35 备份文件的校验项（缺一不可）

| 项 | 校验内容 | 不通过时的判定 |
|---|---|---|
| ① 可读取性 | 文件能被选中并读入（不是 0 字节、不是被截断、不是无权限） | **文件无法读取** |
| ② 格式 | 可解析为 JSON（不是改后缀的 zip/图片、不是半截文件） | **JSON 格式错误** |
| ③ 版本 | 存在版本标识，且属于本应用支持的版本区间 | **备份版本不兼容** |
| ④ 必需结构 | 必需的顶层分区齐全（孩子、任务/模板、积分流水、宠物经验、连续记录、设置等），类型正确 | **必需字段缺失/类型错误** |
| ⑤ 关联完整性 | 任务引用的孩子存在、流水引用的孩子存在、兑换引用的奖励存在；无孤儿记录 | **数据校验失败（引用断裂）** |
| ⑥ 二进制完整性 | 若备份含照片等 Blob：其编码/长度/校验值必须与元数据一致，可完整还原 | **附件数据不完整** |
| ⑦ 规模合理性 | 记录数量、单条长度、总大小不超过浏览器可承受范围 | **数据规模异常**（提示文件可能被篡改或损坏） |

| 项 | 规则 |
|---|---|
| 校验顺序 | 严格按 ①→⑦ 顺序，**第一个不通过的项即终止**，只报这一项原因（不给家长一串技术清单） |
| 校验副产品 | 通过后计算出一份"恢复摘要"：备份时间、备份版本、孩子数、任务数、流水数、连续记录数、**每张表的记录数**、**备份文件字节数**——用于二次确认弹层展示（见 IR-36 第 2 步）与第 6 步逐表比对 |
| 禁止 | ❌ 跳过版本校验（版本不兼容的数据写进去会造成字段缺失的"看似正常"状态）❌ 边写边校验（先污染再发现）❌ 用"文件很大/很复杂"当作失败理由而不给具体项 |

**前置：大小与空间预检（v0.4 新增，与上面七项并行，不是第八项校验）**

| 项 | 规则 |
|---|---|
| 做什么 | 在读取校验的同时给出两项数字：①备份文件大小 ②浏览器报告的可用空间**估算** |
| 为什么不能算"校验项" | 七项校验判断的是"文件对不对"，空间判断的是"能不能装下"——文件完全正确也可能装不下。两者的失败出口不同（前者换文件，后者清空间），所以并列而不合并 |
| 风险提示的措辞 | 空间明显不足时：「这台设备的空间可能不够，恢复有可能中途停下」。**必须出现"可能"**。空间看起来够时**不提示**，但也**不得**说"空间足够" |
| 是否阻止继续 | **不阻止**。由家长决定是否继续（他可能刚清过空间），但要把风险说在前面 |
| 禁止 | ❌ 把估算值写成"已确认可用空间" ❌ 用估算值自动阻止 ❌ 用估算值判断恢复成功（成功的唯一依据是 IR-37 七条） |

### IR-36 数据库不可用时的重建 + 恢复流程（9 步）

| 步 | 阶段 | 界面 | 动作（行为规格，技术实现由 Trae 提方案） |
|---|---|---|---|
| 1 | 选文件 | 异常页 →「从备份恢复」→ 系统文件选择 | 允许在**无数据库**状态下打开文件选择器（不依赖任何业务数据） |
| 2 | 读取与校验 | 全屏进度：「正在检查备份文件…」 | 在**临时内存/临时存储**中读取并执行 IR-35 全部校验 + 大小与空间预检；此阶段**不打开、不创建业务库** |
| 3 | 展示恢复摘要 + 二次确认 | 弹层（不可下滑关闭）：备份时间、版本、数据量（含每表条数与备份体积）、可能的空间风险、**"这会重建本机的本地数据库"** 的明确说明；按钮 `取消` / `重建并恢复`（危险色，需二次点击） | 未确认前，库保持原状（打不开也保持打不开，不做任何破坏性动作） |
| 4 | 重建目标库 | 全屏：「正在准备本地空间…」 | 在获得前面确认后，才尝试**重新初始化**目标数据库（必要时清理旧的损坏库结构）。**此步失败 → 直接进 IR-38 终止态**，不再继续 |
| 5 | 写入 | 全屏：「正在恢复数据 3/7」 | 在**单个事务**内写入全部业务数据（孩子、模板、实例、流水、经验、连续记录、设置、二进制）。写入过程中不得分批"先提交一部分" |
| 6 | 校验恢复结果 | 全屏：「正在核对…」 | 按 IR-37 逐项核对（分表条数、关联完整、积分汇总、宠物经验、附件可读）；任何一项不符 → 判定失败 |
| 7 | 结果落定 | 成功 / 失败 | 成功才写"上次恢复时间"等元数据；失败按 IR-38 处理，且**不得留下半成品库被当作正常数据** |
| 8 | 重新加载 | 成功页：「恢复好了，正在重新打开」 | 重新加载应用，进入正常界面（回 P-C1 或家长端首页，按当时会话） |
| 9 | 结束 | 正常业务界面 | 首次进入后提示一次「已从 X 月 X 日的备份恢复」，不重复提示 |

| 项 | 规则 |
|---|---|
| 事务性 | 第 5 步必须是"全成或全败"。若运行环境无法保证单事务，必须在失败后**清除本次写入的部分数据**并回到不可用状态，不得留下可被当作正常数据打开的半成品 |
| 半成品判定 | 写入失败后若库仍可打开且含部分数据，**必须**在重载后强制识别为"恢复未完成"（例如写入完成标记缺失 → 走 F2 界面，禁止进入业务界面）。**不允许**靠"用户没注意"混过去 |
| 幂等 | 恢复动作不得因为"用户连点两次"而写入两份数据：确认按钮点击后立即禁用，直到流程结束 |
| 空间估算 | 预检给出的可用空间只是**估算**，不得当成写入成功的保证（见 IR-35 前置表） |
| 失败兜底 | 见 IR-38；**任何失败都不得改变用户手上的备份文件** |
| 禁止 | ❌ 在第 3 步确认之前重建或清空任何库 ❌ 分步提交 ❌ 恢复后不校验就显示成功 ❌ 成功后再次弹出"导入"提示造成重复导入 ❌ 自动重试重建（浏览器策略类失败重试无用） |

### IR-37 恢复成功的判定标准（不是"点了文件就算成功"）

**成功必须同时满足以下 7 条，缺一条即判失败：**

| # | 判定项 | 判据 |
|---|---|---|
| 1 | 写入无异常 | 第 5 步事务完整提交，无中止、无配额错误 |
| 2 | 库可重新打开 | 用完即关再重开一次目标库，能正常打开且版本正确（证明不是"写进去但打不开"） |
| 3 | **分表记录数一致** | **逐表**与备份摘要相等：孩子 / 任务模板 / 任务实例 / 审核记录 / 积分流水 / 宠物经验 / 连续记录 / 奖励 / 设置。**禁止只比"总记录数"**（一张表多 2 条、另一张少 2 条，总数相同却已经错了） |
| 4 | **关键关联完整** | 任务引用的孩子存在、流水引用的孩子存在、兑换引用的奖励存在、实例引用的模板存在；**无孤儿记录、无悬空引用、主键无重复** |
| 5 | **积分汇总正确** | 每个孩子星星合计 = 该孩子全部流水变动值之和，且与备份中的合计相等；流水条数一致 |
| 6 | **宠物经验完整** | 每个孩子等级、当前经验、升级所需经验与备份一致；经验流水条数一致；**经验必须独立核对，不得用星星合计代替**（K11 要求两套账分开） |
| 7 | **附件可读**（⚠️ **依赖 G-01 裁决**） | 若备份含照片等 Blob：**数量一致 + 总字节数与元数据一致 + 抽样可解码**（只验字节存在不算可读） |

| 项 | 规则 |
|---|---|
| 抽样 | 第 3、5 条在数完条数后，**必须**随机抽若干条真正读出来看字段完整（防"数量对、内容空"）。抽样是验证方法，不是第 8 条判据 |
| 判据 7 的生效条件 | **G-01 未裁决前按"规格已写、实现待定"处理**：若第一版最终不含附件 → 记"不适用"并写明原因；若含附件 → 必须项，不得跳过 |
| 成功后展示 | 「恢复好了」+ 一行摘要：`来自 11月18日 的备份 · 2 个孩子 · 128 条任务`；随后自动重新加载 |
| 成功后元数据 | 记录"上次恢复时间"，但**不**把"上次导出时间"改成现在（恢复 ≠ 备份，否则备份提醒会被错误清零） |
| 禁止 | ❌ 只校验"事务没报错"就判成功 ❌ 只比总量 ❌ 数量不一致仍显示成功 ❌ 用星星合计代替经验核对 ❌ 附件只数个数 ❌ 用"部分恢复 + 提示稍后补齐"的说辞 ❌ 恢复成功后隐瞒部分数据缺失 |

### IR-38 恢复失败、重建失败与终止态

区分三种失败，**文案与出口完全不同**，不得混为一谈：

| 类型 | 触发 | 界面 | 出口 |
|---|---|---|---|
| **F1 文件问题** | IR-35 任一项校验不通过 | 弹层：具体原因（见 IR-39 文案）+ 已选文件名；**不重建、不动库** | `换一个文件`（回文件选择）/ `取消`（回异常页；若处于正常导入则回 P-P5，当前数据完好） |
| **F2 恢复中断** | 第 5/6 步失败（写入中止、配额不足、校验不符） | 全屏：「这次没恢复成功」+ 明确「本机现在**没有**可用的数据」+ 原因（空间不足/写入失败）+ **不显示成功暗示** | `再试一次`（回第 1 步重新选文件）/ `导出诊断信息`。若因空间不足：先提示清理空间或换设备 |
| **F3 终止态：环境不可用** | 第 4 步重建目标库仍失败（浏览器禁用 IndexedDB、隐私模式、存储策略拒绝） | **终止页**（见下） | **不提供无限重试**；只给诊断信息与更换环境建议 |

**F3 终止页规格（这是本次要求补的终止状态）**：

| 元素 | 内容 |
|---|---|
| 标题 | 「这个浏览器现在用不了本应用」 |
| 说明 1 | 「不是备份文件的问题——文件已经检查过了。是这台设备上的浏览器不允许本应用保存数据。」 |
| 说明 2 | 「你的备份文件还在，换一个浏览器（或换一台设备）打开本应用，再用同一个文件恢复就可以。」 |
| 诊断信息（可折叠） | 环境标识、库打开失败阶段、错误类别（**仅类别，不显示堆栈**）、时间 |
| 按钮 1 | 「复制诊断信息」（便于反馈给开发者） |
| 按钮 2（弱） | 「再看一遍说明」→ 展开常见原因（隐私/无痕模式、浏览器禁用了站点数据、企业策略限制） |
| **禁止** | ❌ 提供「重试」主按钮（同一环境重试必然再失败，会让人误以为有机会）❌ 说成"导入失败请重试"（把环境问题归因为文件问题）❌ 显示"恢复成功/部分成功" ❌ 引导删除备份文件 ❌ 提供"先用着空数据"的入口 |

| 项 | 规则 |
|---|---|
| 判定依据 | 是否进入 F3，只看**重建目标库这一步**是否失败，与文件校验结果无关 |
| **终止的范围（v0.4 明确）** | 终止的是**本次流程**，不是用户**永久失去恢复权利**。不提供"同页面重试"，但用户修复环境后（退出无痕、允许站点数据、清理空间、换浏览器/设备）**重新打开应用**，会重新从 I 组判定开始，并可再次走恢复流程；备份文件始终有效 |
| 重试策略 | F1/F2 允许用户**手动**重试；F3 不提供重试，只在用户主动"复制诊断信息"后结束。**任何情况都不做自动重试循环** |
| 禁止 | ❌ F1/F2/F3 共用一套文案 ❌ 在 F2 后显示"数据已恢复一部分" ❌ 在 F3 上假装稍后会自动恢复 ❌ 在 F3 写"永久无法恢复/数据已丢失"（与事实不符：文件还在，换环境可再试） |

### IR-39 备份文件异常的分级提示与"重新选择文件"闭环

| 失败类型 | 家长看到的文案（人话，不提技术词） | 下一步 |
|---|---|---|
| 文件无法读取 | 「这个文件打不开，可能没下载完整」 | `换一个文件` |
| JSON 格式错误 | 「这个文件不是本应用导出的备份」 | `换一个文件` |
| 版本不兼容 | 「这个备份是更新（或更旧）的版本做的，当前版本打不开」 | `换一个文件` / `取消` |
| 必需字段缺失 | 「这个备份缺了一部分内容，恢复出来会不完整」 | `换一个文件` |
| 附件/图片不完整 | 「备份里的照片有一部分读不出来」 | `换一个文件` / `仍然恢复（不含这些照片）`（**仅当主体数据完整时提供**，且必须在按钮上写明后果） |
| 数据校验失败（引用断裂等） | 「这个备份里的记录对不上，不敢直接恢复」 | `换一个文件` |
| 规模异常 | 「这个文件大得不正常，可能不是备份文件」 | `换一个文件` |

**闭环要求**：任何一类失败后，`换一个文件` 必须能直接重新打开文件选择器，**不需要退回首页再进来**；已选文件名与失败原因保留在界面上，直到用户换文件或取消。

| 项 | 规则 |
|---|---|
| 不破坏原则 | 校验失败阶段**不触碰任何现有数据**；正常导入场景下当前数据保持完好 |
| 文件保留 | 失败后**不删除、不移动**用户的文件；原文件可在任何设备、任何时间再次尝试 |
| 禁止 | ❌ 失败后自动重试解析 ❌ 把不同原因合并成"导入失败" ❌ 在校验失败时替换现有数据 ❌ 删除原始备份文件 |

### IR-40 读取部分失败不得解释为"空家庭"

| 项 | 规则 |
|---|---|
| 触发 | 数据库能打开，但某个表/查询读取抛错，或返回结果明显不完整 |
| 必须 | ① **不得**把读取失败渲染成空列表、0 个孩子、0 颗星星 ② **不得**把部分读取结果当作完整家庭数据继续展示（例如只读到 2 个孩子就显示"2 个孩子"）③ 明确标出**哪一块**出错（"任务暂时打不开"而不是整页崩）④ 提供 `重新读取` / `重新加载` / `从备份恢复` 三个合理出口 |
| 分块隔离 | 页面按区块降级：任务区失败不影响宠物区、流水区；失败区块显示错误卡，其他区块正常 |
| 计数类展示 | 任何"共 N 条 / N 个孩子"的数字，若来源查询失败，**显示"—"而不显示 0** |
| 禁止 | ❌ 读取失败自动清空数据库 ❌ 用"暂无数据"掩盖异常 ❌ 把部分结果用于统计、导出或备份覆盖判断 ❌ 因单表失败跳到全屏终止页（那是 IR-32 的 E3-c1 才做） |

### IR-41 删除全部家庭数据（G-05，**D2 待 Owner 确认**）

> 依据 `PRD_v1.3.md` §11.6。入口在 P-P5「危险操作」分组（`01` §3.5 / §3.6），状态见 `02` §8.7。
> **为什么值得单开一条规则**：它和 IR-16（导入=覆盖恢复）都是"会让数据消失"的动作，但目的、验证方式、结果、失败后果完全不同。若合并进 IR-16，实现时必然共用一套确认文案，家长分不清"我是要找回还是清空"——这是本项目后果最重的一次误操作，必须独立。

| 项 | 规则 |
|---|---|
| 入口位置 | P-P5 **最底部**「危险操作」分组，一行灰色文字按钮「删除全部家庭数据」+ 一行说明「删除后无法恢复」。**不是实心按钮、不排在其他分组中间** |
| 前置 1：进入家长模式 | 必须在家长模式内（P-P5 本身已在家长模式下） |
| 前置 2：**重验 PIN** | 点击入口后**必须重新输入家长 PIN**，即使当前已在家长模式。理由：家长模式可能被孩子趁家长离开时接管（K5 说明 PIN 只是误触屏障），删除不可逆，必须再确认一次操作人。**不得**用"已在家长模式"跳过 |
| 前置 3：二次确认 | 范围说明层（不可下滑关闭）+ 必须勾选「我知道删除后无法找回」后，`永久删除` 才可点；未勾选为禁用态 |
| 范围说明（缺一不可） | ①**会删什么**：全部孩子资料、任务与模板、审核记录、星星流水、宠物等级与经验、连续学习记录、奖励、家长 PIN 与恢复码 ②**不会删什么**：你自己保存到设备上的备份文件 ③**能否找回**：有自己保存的备份才能恢复，没备份就找不回 ④**这不是"恢复备份"**：删除和恢复是两个独立操作 |
| 执行 | 单事务清空全部业务表；界面全屏「正在删除…」，无按钮、不可返回、不可交互 |
| 成功判定 | ①事务提交无异常 ②清空后重开库校验为**空**（不是"以为空了"）③再次进入应用不做任何自动生成。三条全过才算成功 |
| 成功后 | 重新加载 → **P-C1 空家庭态**（「还没有小朋友，请家长先设置」）→ 家长首次设置 PIN → 添加孩子。**不得**停在半空界面，也**不得**自动弹出"是否恢复备份" |
| 失败处理 | 分三档说清，均**不得显示成功**：①完整回滚 → 「没删掉，数据还是原来的」②已删一部分 → 「有一部分删掉了，有一部分还在」+ 建议先导出再重试，**中间态家庭必须显式标注不完整**，不得渲染成正常家庭 ③读不出当前状态 → 转全屏异常页（IR-32），禁止说"已删除" |
| 与恢复的关系 | **禁止合并**：不得做成"删除并恢复"一个按钮/一条流程。删除后若要恢复，必须由家长**另行发起**恢复流程（IR-34 起） |
| 删除范围边界 | 删除的是**本机家庭数据**，不是应用本身：不注销 Service Worker、不卸载应用、不动用户在文件系统上的备份文件 |
| 禁止 | ❌ 删除用户设备上的备份文件，或提示"备份也已删除" ❌ 删除失败显示成功 ❌ 只删孩子资料而遗留任务/流水/经验/附件 ❌ 只删记录不清 Blob（若含附件，见 G-01） ❌ 与恢复备份混为一项 ❌ 在数据库异常页或终止态页提供该入口（故障时不得引导销毁唯一副本） ❌ 删除后保留家长 PIN 与恢复码（会留下"旧家庭仍有效"的错觉） |
